Unity CLI 1.0：与 Pipeline 包一起退出测试，可在终端和 agent 里驱动编辑器

Unity 在 Unite Tokyo 宣布，Unity CLI 与 Pipeline 包（com.unity.pipeline）已结束测试，推出 1.0。文中回顾：2026-07-15 起提供可在终端安装和管理 Editor、模块与项目的测试版二进制；Pipeline 包可让 CLI 驱动本机已打开的 Editor，供脚本或 agent 打开项目、执行命令并检查结果。最新 Unity Hub 会一并安装 CLI。官方为 Claude Code、Codex、Grok Build 和 Google Antigravity 提供插件，并在公开的 Unity skills 仓库提供同样的技能。文中给出的使用统计（未在本机独立核实）：自 7 月 20 日起，超过 35 万已登录用户累计运行超过 6 亿次命令，其中约 98% 来自编程 agent 和其他自动化。1.0 相对测试期的变化包括：`unity setup` 可安装上述官方插件；`unity skill install --all` 把技能装到本机已发现的各类 agent（文中点名 VS Code、GitHub Copilot、Qwen Code 和 OpenCode），`unity skill sync` 用于保持更新；CLI 可识别并应答 Editor 正在等待的对话框，避免远程或无人值守会话卡在看不见的弹窗；`unity build --target` 可在已打开该项目的 Editor 里构建，`unity pipeline cloud-build` 可从终端配置云构建目标；`unity vcs` 能标出场景或预制件中变更对应的资源，并可在不切换分支的情况下摘要 pull request；`unity projects create` 会为新项目加入 Pipeline 包，并可安装项目所需 Editor；`unity open --until-ready` 会等到 Editor 可以接受命令；列表与数据流的 JSON 形状统一，短选项含义一致，`--project-path` 处处可用，CI 中不会交互式提问，并可用退出码区分 Editor 忙碌、对话框阻塞或网络中断，还可按项目锁定 CLI 版本范围；`unity projects audit` 可运行 Project Auditor 并按升级、优化或 URP 等焦点写报告；提供 macOS / Linux / Windows 原生二进制及 Homebrew、winget、APT 安装，`unity self-update` 会保留最近三个版本以便回退，也可用 `unity docs cache add` 缓存离线文档。文中还写到针对安装、技能和项目关联的安全修复，使克隆下来的仓库不能用自带程序顶替正版工具；这些修复的实际效果本机未做安全审计。1.0 承诺在 1.x 内保持命令、选项和输出兼容，必须改动时会先给弃用警告并留出迁移时间。Build Server 许可现已覆盖 agent 和自动化（不只是构建）：每个实例一份许可，可在无头 Editor 或容器中运行 agent。文中预告即将提供面向 CI、构建机和 agent 的 Linux 容器化 Editor，目前尚未发布。本机未安装或运行 Unity CLI。

    Pose-based Neural Clothing：面向动画角色、可实时交互摆姿势的神经服装（SCA 2026 论文）

    DisneyResearch|Studios、ETH Zürich 与 Pixar Animation Studios 的论文《Pose-based Neural Clothing for Animated Characters》于 2026-11-13 提交 arXiv（cs.GR），注释写明已被 ACM SIGGRAPH / Eurographics Symposium on Computer Animation（SCA 2026）接收，并将发表于 Computer Graphics Forum。针对传统服装模拟速度慢、调参费时，以及现有神经服装方法多在写实人体（如 SMPL）数据上表现较好、在动画角色数据上对未见姿势泛化较差的问题，作者设计网络与训练策略，以便在实时条件下更好地泛化到未见姿势，支持交互式摆姿势。设定是面向制作流程：为单件服装、在准静态条件下训练。方法先训练变分自编码器（VAE）得到平滑且有表达力的隐空间，再逐步把 VAE 编码器从重建过渡到由姿势驱动的预测；预测同时以低维姿势参数和角色体表位移为条件。此外提出一种局部梯度直方图损失，用于减轻重建损失造成的过度平滑。论文称在制作级资产和公开数据集上，该方法能实时生成清晰真实的褶皱、平滑的大尺度垂坠，并保持时间连贯。文中测量：在 Jen’s Shirt 数据上推理速度为 212.2 FPS，实验在 NVIDIA GeForce RTX 4070Ti 上进行；还与 Maya 2025.2、Unreal Engine 5.6 以及若干已有神经方法做了误差与观感对比，并报告用户研究中 96.3% 的投票更偏向该方法。这些速度、误差和用户研究数字均来自论文，本机未复现训练或推理。碰撞处理在推理时于变形之后进行，作者称只做小幅修正。准静态假设对非常松弛、动态很大的服装仍可能吃力，文中也提到在 VTO 等数据上各方法都可能出现过平滑或高频伪影。

    AMD FSR UE 插件更新至 4.1.2：FSR Upscaling 4.1.2 覆盖 RX 6000 与部分锐龙核显

    Alexander Blake-Davies 宣布 AMD FSR Unreal Engine 插件更新到 4.1.2，把 FSR “Redstone” SDK 2.4 的更新带到 UE 5.3–5.8。ML 超分此前已覆盖 RX 7000，此版本扩展到 RX 6000（RDNA 2 独显）以及部分带 Radeon 核显的锐龙处理器（游戏本、迷你 PC 和掌机）。4.1.2 使用两套 INT8 模型并按硬件自动选择：RX 6000 与锐龙 AI Max 跑完整模型，面向更受限核显的优化模型体积不到一半；其他硬件回退到分析式 FSR 3。插件通过 FSR API 接入，已集成的游戏也可随 Adrenalin 驱动获得更新的 FSR 版本，不必每次改游戏侧。插件目前只支持 DirectX 12；SDK 2.4 里已有的 Vulkan 超分与帧生成尚未进入此插件。同期包含 FSR Frame Generation 4.0.2 与 Frame Generation Swapchain 4.0.0：在 RX 9000 上增加 Driver-Assisted Frame Pacing，需 Adrenalin 26.10.1 或更新，并配合插件默认的 OverrideSwapChainDX12=true；FSR Frame Generation 4.0.2 要求 Windows 11。Anti-Lag 2 插件同步更新到 2.0.6，可与 FSR 帧生成一起使用。配套指南写明安装包支持 UE 5.3 至 5.8。

DIRT：用深度补全与双频段混合做无需训练的实时新视角合成（论文）

Friedrich-Alexander-Universität Erlangen-Nürnberg 的论文《DIRT: Depth-completed Image-based Rendering using Two-band Blending for Live Novel-view Synthesis》于 2026-11-13 提交 arXiv（cs.CV，交叉列出 cs.GR）。针对多数新视角合成方法需要按场景优化、难以用于拍摄过程中的实时（live / ad-hoc）合成，作者提出一种传统图像绘制路线：输入是带位姿的深度传感器观测和图像，不使用神经网络，也不做场景优化或训练。流程是：把主动传感器得到的稀疏点几何投影到目标视角的屏幕空间，在该深度缓冲上做层次化深度补全；再把若干带位姿的图像投影到该代理几何上并处理遮挡；最后用考虑频率的双频段混合，并以近似距离变换作为混合权重。因此在捕获与新视角绘制之间不必等待按场景训练，也不依赖网络对未见场景的泛化。作者在手持 RGB-D、车载 LiDAR、热成像以及低光照等设置上做了验证。实验在同一台机器上进行（Intel i9-12900、NVIDIA A5000 24 GB、64 GB 内存），主要延迟指标定义为最后一路输入传感器数据到达至合成测试视角之间的 capture-to-image 间隔，质量指标为 PSNR 与基于 AlexNet 的 LPIPS。论文称在实时重建场景上优于所比较的先前方法，在常规离线新视角基准上保持有竞争力的结果；例如 Table 3 在 LiveNVS 数据集、使用已采集的立体深度时，作者方法报告 LPIPS 0.1987、每张图 8.51 ms，对照 nvblox TSDF 融合为 0.2438 / 74.39 ms。这些数字和“优于先前方法”的判断均来自论文实验，本机未复现。该方法依赖带位姿的深度观测，不是无位姿纯 RGB 方案。

GitHub 于 2026-11-16 发布变更说明：自当天起，Claude Opus 4.8、Claude Opus 5 和 GPT-5.6 Terra 已在多数 GitHub Copilot 体验中弃用，范围包括 Copilot Chat、行内编辑、ask / agent 模式以及代码补全。这批弃用此前已在 2026-10-15 公告。建议替代为：Claude Opus 4.8 与 Claude Opus 5 改用 Claude Opus 5.5，GPT-5.6 Terra 改用 GPT-6.1 Sol 或 GPT-6 Luna。例外：个人年度订阅的 GitHub Copilot 用户仍可使用 Claude Opus 4.8。Claude Opus 5 已从模型选择器中移除，但在已有授权访问下仍可用于运行时的拒绝回退（runtime refusal fallback）；既有的企业模型策略继续有效。在默认启用模型的情况下，建议的替代型号会自动对 Copilot Enterprise 和 Copilot Business 客户开放，除非管理员关闭了全局默认或明确禁用了该模型；若已关闭全局默认，需在 Copilot 设置的模型策略中手动启用替代型号。启用后，用户可在受支持体验的 Copilot Chat 模型选择器中看到它们。移除已弃用模型无需额外操作。本条与 11-15 精选中“12 月 14 日将下线 6 个模型”不是同一批型号。本机未登录 Copilot 核对选择器的实际显示。

Neural Render Proxies：用一次与灯光无关的路径采样，对固定机位场景做可微、交互式重打光

ETH Zurich 与 DisneyResearch|Studios 等机构的 Sergio Sancho、Alexander Rath、Marco Manzi、Pascal Chang、Amit H. Bermano、Derek Nowrouzezahrai、Markus Gross 与 Marios Papas 的论文 Neural Render Proxies for Interactive and Differentiable Lighting，于 2026-11-12 提交到 arXiv（2611.17185v1，cs.GR）。页面标注该文属于 2026 年 Eurographics Symposium on Rendering（Computer Graphics Forum 第 45 卷第 4 期，编辑 I. Gkioulekas 与 A. Jarabo）。方法针对灯光环节里几何、材质和相机已固定、但每次微调灯光都要用离线渲染器重跑全图的情况：把渲染拆成一次与灯光无关的路径采样，以及之后按灯光参数计算发光。先从相机按 BSDF 重要性采样（不含 Next Event Estimation）缓存路径数据，再训练一个场景专用的轻量网络，学习从场景中任意位置到像素的光传输；推理时只随分辨率和灯光数量、参数规模变化，而不随场景与外观复杂度增长。作者写该方法可与不可微的生产渲染器配合：制作场景用 Walt Disney Animation Studios 的 CPU 渲染器 Hyperion 采集路径，学术场景则另做采集。摘要给出的交互式重打光帧率为约 30–60 Hz，并接近路径追踪参考；网络可微，因而可用图像空间编辑或生成式目标，对灯光参数做基于梯度的反求。实现基于 PyTorch 与 tiny-cuda-nn。作者在一块 RTX 5090（32 GB 显存）上报告：标准配置（680×680、512 spp、8 层×256 神经元）训练 10 万次迭代约 1 小时；Kitchen 场景（885×500）上，256/8 网络推理 9.13 ms、模型 7.4 MB，512/8 为 31.21 ms、13.3 MB。用与灯光无关的 64 spp 路径数据训练时，色调映射空间的平均 PSNR 仍比最多 1024 张图的基于图像基线高 2.8 dB。限制包括：机位与材质需固定；训练后不能再改物体间的非物理衰减或灯光独占（分层 NRP 只能近似后者）；遮挡腔体可能欠采样；路径数据需预载进显存。上述帧率、耗时、显存和 PSNR 均来自论文，本机未训练或复现。

论坛：UE 5.8 Vulkan 硬件光线追踪下 bindless 描述符延迟写入导致 GPU hang（含补丁）

LifeBandit7575 报告：UE 5.8 的 Vulkan RHI 在默认开启的 bindless（VK_EXT_descriptor_buffer）下，FVulkanShaderResourceView / FVulkanUnorderedAccessView 会在构造函数里分配 bindless 槽位，但描述符要等 RHI 线程的 EnqueueLambda 才写入；若命令列表先提交，GPU 会读到该槽位的前一个所有者（硬件光线追踪时常见为加速结构或 3D 纹理），顶点着色器取用后就会 GPU hang。发帖人在 Linux、Intel Arc A750、Mesa ANV 26.2.6 / 26.3.0 上，用约 300 个每帧重建顶点缓冲 SRV 的 UMaterialBillboardComponent（半透明加法材质），在 -game 中打开 r.RayTracing.Enable 1 并配合 r.RayTracing.Shadows 1 或 r.Lumen.HardwareRayTracing 1 后复现：启用 RT 后约 6–74 秒出现 hang（中位数约 13 秒），一晚超过 40 次。补丁是在构造函数里也对 buffer view（不含加速结构）调用 UpdateView；按发帖人验证，11/11 次通过（8 次 RT 阴影、2 次 Lumen HWRT、1 次关闭 RT）且未见回归。该帖尚未提供空白工程复现，也还没有 Epic 官方确认。

Last Week in Unreal：ue6-main 取消编辑器进程内 cook，项目级 cook 必须改走 cook commandlet

SpeedrunCI 于 2026-11-09 发布 Last Week in Unreal，汇总 2026-11-02 至 11-08 对 EpicGames/UnrealEngine 源码分支的提交。作者把该周最可能打断现有流程的变化放在 ue6-main：提交 84cd4dab 的说明是“Cooker: Remove support for cooking in the editor process（UUnrealEdEngine::CookServer，以及 ECookMode::CookOnTheFlyFromTheEditor / CookByTheBookFromTheEditor）；all project cooks must now run through the cook commandlet”。提交还写，这是接续 5.7 里把编辑器中的 CookByTheBook 弃用之后的收尾，并“deletes (without deprecation)”原先可通过 CookerSettings.bEnableCookOnTheFlyFromTheEditor 使用的编辑器内 CookOnTheFly。文中整理的仍然可用或受影响的行为包括：单个包仍可在编辑器里通过 UE::Cook::Internal::CookAsset 烹饪，但对某些类可能与项目级 cook 不一致；已保存的 Launcher 配置若使用了编辑器内 cook 模式会被重映射，并给出警告，改为在单独的 cook 进程里做 By the Book 或 On the Fly；Launch On 仍可用，但会启动单独的 cook 进程；Launcher 配置上的 OnIsCookFinished()、OnCookCanceled() 委托被删除，cooker 设置里的 bEnableBuildDDCInBackground 也被去掉。因此，依赖编辑器进程内 cook 或上述委托的插件和工具将无法编译，也没有弃用过渡期。同一周 CookIncrementalVersion 被改了三次（b7d89bd1、d6ecb330、2441c767），提交说明分别是主资产扫描规则、Shader 变化和重复主资产 ID“not picked up”，每次都会让下一轮增量 cook 失效全部包；另外 6ea64332 修了 PreSave 期间创建的对象丢失 cook 依赖的问题，复现是“cook 一个 Niagara 系统，改它的 renderer MIC 的父材质，再做增量 cook：该系统不会被重新 cook”。这是对公开源码提交的解读，不是已发布引擎版本的发行说明；文中统计该周 ue6-main 有 1,476 个提交。文章同时也介绍了当时刚公开、尚未打标签的 5.9 分支，并写 Preview 将在“下周”到来——5.9 Preview 现已发布，相关官方说明此前已另文收录，此处不重复展开。本机未同步这些提交或实际 cook。
