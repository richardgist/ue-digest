LMnOP：用 leave-many-out 重要性修剪 3D 高斯溅射，高比例删除后无需微调仍多数指标领先（论文）

MOBILTECH 与庆熙大学作者在 arXiv 发布 LMnOP（提交于 2026-11-23）。文中指出，3DGS 场景常需数百万个高斯，存储与绘制成本高；常见的 leave-one-out 重要性是单独去掉一颗高斯时的损失增量，在高修剪比例下会漏掉“单独看冗余、一起看却必要”的高斯。LMnOP 改为估计 leave-many-out 重要性：其他高斯也被随机去掉时，再去掉某一颗所带来的平均损失增量。作者给出像素颜色在随机删除下的均值与方差的闭式计算，据此近似重要性，而不必抽样删除模式；再按重要性更新每颗高斯的保留概率，最后一次性修剪。三个数据集（Mip-NeRF360、Deep Blending、Tanks & Temples）在 90% 与 99% 删除、且修剪后不微调的对比中，作者报告 LMnOP 在 18 项指标里有 16 项最好；SSIM 与 LPIPS 在全部 13 个场景上都优于 GaussianPOP。两个例外是 90% 删除时 Deep Blending 与 Tanks & Temples 的 PSNR，GaussianPOP 更高（分别为 27.69 对 27.22、20.81 对 20.15）。在 Mip-NeRF360 上，相对 GaussianPOP 的 PSNR 优势从 90% 删除时的 0.45 dB 扩大到 99% 时的 1.15 dB（99% 时 LMnOP 为 16.53 dB，GaussianPOP 为 15.38 dB）。耗时方面，作者在 Mip-NeRF360 上测得 LMnOP 每场景 19.5 分钟（90%）和 17.0 分钟（99%），GaussianPOP 为 0.9 与 0.6 分钟。另用 5,000 步微调 90% 删除后的 Mip-NeRF360 模型后，作者称 LMnOP 在 PSNR、SSIM、LPIPS 上仍最好。以上数字与对比均为论文结果，本机未复现；文中未见官方代码仓库。

  3. 图形渲染UE 日报04

    论坛：UE 5.8.4 在 Vulkan 下，32768 宽的 VSM 图集让体素化 Nanite 树丢失投影

    作者 @EK_Studio 报告：在 UE 5.8.4 中，开启 Nanite Foliage 与 Virtual Shadow Maps 并保留 VSM cache 时，Shape Preservation 设为 Voxelize 的静态 Nanite 树会在物理 VSM 图集宽为 32768 像素时丢失全部或部分投影；树本身仍可见，同场景里的普通网格投影正常。问题先在 Linux/Vulkan 打包版出现，后又在 Windows/Vulkan 编辑器里复现（Windows 对照硬件为 RTX 4080 Laptop，驱动 610.91）。用 r.DumpRenderTargetPoolMemory 确认 Shadow.Virtual.PhysicalPagePool 为 32768 宽后，整棵树的影子会消失，或相邻几棵树的影子被切成矩形缺口。两次本地运行都使用 256 MiB 的 R32_UINT 池、两层 array；把 Vulkan Profiles 层的 maxImageDimension2D 报成 16384 后，同一容量的池变为 16384×2048，丢失的影子会回来。作者指出 NaniteRasterizer.usf（CL 58902052，约 1279、1309–1313、1688 行）里，GroupSourceLaneAndPixelPos 把 lane 索引、X、Y 分别打进 5、14、13 位，而单页 VSM 路径使用的是物理图集坐标；例如 (16384, 0) 会被解码成 (0, 1)。发帖时还没有 Epic 答复。

Claude Ship：可在 GitHub 上审 PR、修 CI，并按仓库策略决定是否批准（Team/Enterprise，部分功能为 beta）

Anthropic 于 2026-11-23 发文介绍 Claude Ship（文中写“即日起以 beta 提供”）。它由已正式可用的 Code Review，以及仍处 beta 的 PR Steward 与 Claude Approvals 组成，用于在 GitHub 上把 pull request 走过审阅、修复和批准决定。Code Review 可从多角度审查并发布发现，并提供 Quick / Standard / Deep 三档；PR Steward 处理失败的 CI、合并冲突以及来自 Code Review、其他工具或同事的反馈，但不设计为批准或合并 PR，每次推送后会说明改了什么以及如何撤销，也可用 @claude 指令或 @claude stop。Claude Approvals 读取仓库里的策略文件，在策略允许时自行批准常规改动，或要求更深的人工签署；官方建议多数客户先开 observe-only 模式，再把它纳入分支保护。开发者可在 Claude Code 里用新的 /ship 命令：推送并开 PR、审阅，并跟进反馈与失败检查；/ship 自当日起在 Claude Code 与桌面应用中逐步推出，最终能否合并仍取决于开发者权限和仓库分支规则。管理员可按仓库打开 Code Review 与 PR Steward，配置审阅级别、触发时机和花费上限。适用范围：Claude Team 与 Enterprise，且仓库在 GitHub 上。用量按 token 计费，可能增加组织成本；Claude Approvals 无基础费用，但策略中的分类器按 token 计费，且策略若使用 Claude 的审阅会触发一次计费的 Code Review（observe 模式也一样）。运行 /ship 计入常规 Claude Code 用量。Zero Data Retention、HIPAA 配置或客户管理加密密钥的组织不可用。文中还提到符合条件的 Enterprise 组织可在领取后 30 天内使用至少 10,000 美元 Claude Ship 积分，须在 2027-01-15 前领取，条款适用——这是厂商优惠。另称 Claude Code 团队在把 Claude 的审阅作为更广流程一层时，6 月至 9 月已合并 PR 数量增加一倍以上、被回退比例下降超过 40%；该数字为 Anthropic 自己的团队统计，本机未复核，也未实际使用 Claude Ship。

论坛：Launcher 版 UE 5.8 无法做 iOS Metal SM6；METAL_SM5_IOS 未声明 GPU Scene，Nanite 回退网格会画成大平面

作者 @NearBison6274 在 iPad Air（M4，iPadOS 26）上报告了 Launcher 版 UE 5.8 的两处 iOS 问题。其一：要开 METAL_SM6_IOS 需要 bindless，也就需要 Apple 的 Metal Shader Converter；但 Launcher 的 iOS 组件不附带 Engine/Binaries/ThirdParty/Apple/MetalShaderConverter/IOS/libmetalirconverter.embeddedframework.zip。就算手工放入 Metal Shader Converter 4.0 beta 3 的 iOS 库，预编译的 iOS MetalRHI 也是在未定义 METAL_USE_METAL_SHADER_CONVERTER 的情况下编出来的（目标文件里没有 IRMakeTextureResident / IRCompilerCreate），安装版又不能重编该模块，因此 Launcher 引擎在 iOS 上完全无法使用 Lumen。其二：Engine/Config/IOS/DataDrivenPlatformInfo.ini 里，[ShaderPlatform METAL_SM5_IOS] 没有 bSupportsGPUScene=true（Mac 的 SM5 平台有这项）。结果是开启 Nanite 的静态网格走 fallback 时，会在关卡里画成巨大的“漂浮平面”；在该节补上 bSupportsGPUScene=true 后，作者已在真机上确认平面消失。作者还写到：若同时关掉 r.AllowStaticLighting，iOS SM5 渲染器就没有间接光，基于 Lumen 的 PC 项目很难在 M 系列 iPad 上接近原貌。发帖时还没有 Epic 答复。

TSIR：用可光线追踪的三角形溅射做两阶段逆渲染，重建可重打光资产（论文）

Westlake / 浙江大学 / 清华 / 阿里达摩院等作者在 arXiv 发布论文 TSIR（提交于 2026-11-20）。文中指出，重叠的高斯图元会让表面恢复变难，光线传输也需要多层遍历与合成。TSIR 是两阶段逆渲染：第一阶段得到不透明的 triangle splat，并学习顶点着色法线；第二阶段直接在这些表面上做光线追踪，用蒙特卡洛积分估计材质，计入直接光照与间接反射，以减少对多层合成的依赖。作者还给出一种抗锯齿，用来压三角形边界伪影。在 Synthetic4Relight 与 TensoIR Synthetic 上（各四个场景平均），作者报告：Synthetic4Relight 的新视角 / 反照率 / 重打光 PSNR 分别为 40.78 / 35.10 / 36.99，高于所比较的 NvDiffRec、GS-IR、IRGS、GeoSplatting 等；TensoIR 上新视角与重打光 PSNR 为 37.10 与 32.75、法线 MAE 为 3.65°，同样高于这些基线，但反照率 PSNR（34.43）低于 TensoIR 方法本身的 34.86。重打光效率方面，作者在 TensoIR 的 Hotdog、bridge 环境、800×800 上测得 TSIR 为 14.02 FPS、重打光 PSNR 31.24 dB，并写这超过 IRGS 的 0.46 FPS 三十倍以上（两边都用每像素 768 条光照射线）。抗锯齿质量被写为接近超采样（TensoIR 新视角 PSNR 37.10，对 SSAA 的 37.18），且比超采样更高效。以上数字与对比均为论文结果，本机未复现，也未核对该效率表所用 GPU。

论坛：UE 5.8.4 在 GPU 高负载下，Lumen 异步表面缓存光照会把辐射度染成闪烁色块（关掉 r.LumenScene.Lighting.AsyncCompute 可消除）

作者 @NemesisDXB 报告：在 UE 5.8.4、DX12/SM6、默认 Epic 档的 Lumen GI 与 Lumen 反射、并开启 Nanite 与 Virtual Shadow Maps 的情况下，把 GPU 负荷推到接近满载后，一旦打乱帧节奏（实时视口下把鼠标划过 Scene Outliner 即可，不必进 PIE），整面墙和屋顶会以绿、蓝、红、紫、橙等纯色块闪烁或频闪；节奏稳定后会暂时恢复，再次扰动又出现。硬件与软件 Lumen 都能复现。他们的例子是约 40 个带壳层毛发、26.6 万顶点的蒙皮网格，把 RTX 5070 Ti 推到约 96%；同一问题也会在大型开放世界关卡里经过长时间编辑后慢慢出现。逐项开关的结果是：r.LumenScene.Lighting.AsyncCompute 0、r.Lumen.AsyncCompute 0、r.LumenScene.Radiosity 0、r.Lumen.DiffuseIndirect.Allow 0，或把 t.MaxFPS 设为 30（让 GPU 有空闲）都能消除；r.RDG.AsyncCompute 0 无效。r.Lumen.Visualize 13 能在表面缓存间接光里看到这些色块。作者据此认为问题出在异步场景光照 / 辐射度路径的顺序或同步，而不是计算队列本身；显存约 9.8/16 GB，没有驻留警告。发帖时还没有 Epic 答复。

Streaming-AAA：作者称在两块 A800 上以 1080p、43 FPS、198 ms 延迟流式生成可玩的 3A 游戏视频（论文）

腾讯 AIPD 作者在 arXiv 发布 Streaming-AAA（首发 2026-11-19，v2 于 2026-11-20）。这是面向可控制、可无限时长的 3A 游戏视频生成框架，主要针对《原神》。作者写系统由三部分构成：为高分辨率解码重设计的视频 VAE；用 diffusion forcing 预训练并拉长时序训练窗口；以及后训练蒸馏与记忆压缩。实现细节写明：为提高吞吐，扩散模型与 VAE 解码器部署在两块独立的 NVIDIA A800 上做流水线，去噪步数为 2。作者报告在该设置下可生成 1080p 游玩视频，帧率为 43.0 FPS，端到端（动作到像素）延迟 198 ms——由扩散 93 ms、VAE 解码 58 ms，再加上动作可能在半步中途到达而计入的 0.5 步扩散（93×1.5+58）得出。表 2 用 VBench（custom_input，科目一致性、背景一致性、运动平滑、成像质量，在两个评估标题上平均）对比 Lingbot、YUME、Matrix Game 3.0、HY-World1.5：作者报告本方法在科目/背景一致性、成像质量与平均分（0.832）上最高，运动平滑 0.982 略低于 HY-World1.5 的 0.988；对比方法分辨率为 480p 或 720p，帧率约 2.1–6.7 FPS、延迟约 6.6–11.3 秒，硬件设置并不统一（例如 Lingbot 写的是 8 GPU 上 2.6 FPS）。作者还展示连续游玩约一小时的结果，但局限里写明模型主要针对单一游戏、对未见环境与机制的泛化有限。以上速度、延迟、榜分数与“更可玩”等均为作者评测，本机未复现。项目页：https://streamingaaa.github.io/ 。

Last Week in Unreal（11/16–11/22）：ue6-main 将传统光追阴影标为弃用，并给移动端放开 Render Command Pipe

SpeedrunCI 在 2026-11-23 发布的周报统计：11 月 16–22 日 ue6-main 有 1,595 个提交（其中渲染 131 个），公开 5.9 分支 322 个，ue5-main 另有 640 个，5.8 分支本周无提交、也没有 5.8.5 标签。渲染方面，ue6-main 把传统光追阴影标记为弃用，提交说明写“This feature is deprecated by Megalights”；新增只读 CVar r.RayTracing.Shadows.Supported，默认仍为 true，因此目前行为还不变，项目设置则改名为“Ray Traced Shadows (Deprecated)”（47ad9ec9）。新平台标志 bSupportsNaniteRayTracing 允许“在 Nanite 光追太慢、不宜使用的平台上跳过编译相关着色器”，本次 diff 为 Windows、Linux 和 Mac 打开了它（d283815e）；文中提醒：未设置该标志的平台上，若把 r.RayTracing.Nanite.Mode 设为 1 或 2，会回退到 fallback 网格并打出 LogNanite 警告，而默认模式本来就用 fallback 网格。移动端不再被强制 r.RenderCommandPipeMode 0，Android、iOS 和 Switch 改为 mode 1，并写明在 Switch 版《Fortnite》上测得 Game Thread 与 Render Thread 各约 -0.2ms（7a8b450c）。5.9 分支上，Preview 2 里关掉 Virtual Shadow Map 投影数据 uniform buffer 的改动仍在 Preview 2 中；本周又在“UBO 平台且未使用 one-pass projection”时重新启用该 buffer（f615c07d）。

Codex CLI 0.172.0：搜索结果可跳转到线程，斜杠命令支持 Tab 补全，并可按工具设置审批审阅者

OpenAI 在 GitHub 发布了 Codex CLI 0.172.0（标签 rust-v0.172.0，发布时间 2026-11-24T00:03:55Z）。新功能包括：可从搜索结果和 transcripts 中的线程链接跳转到已保存对话以及嵌套的子代理；对受支持的斜杠命令按 Tab 补全参数（例如 `/mcp lo` 补全为 `/mcp login`）；在 agent command center 里用 Shift+Up / Shift+Down 在任务组之间跳转；带有缓存工具列表的可选 stdio MCP 服务器，默认改为第一次调用工具时再启动；可在 `config.toml` 里为单个已连接的 app 工具设置 approval reviewer；app-server 客户端可在设置或登录时选择 Amazon Bedrock Runtime。修复方面，发布说明列出：`codex exec resume` 会恢复已保存的沙箱权限、工作目录和 workspace roots（除非显式覆盖）；远程会话在客户端与服务器操作系统不同时保留工作目录、workspace roots 与可写路径；流式响应里一旦出现供应商错误会立刻报告，并标明触达的是哪一项 API 花费上限；打断父回合时会为下一回合保留子代理已排队的回复；以及用 PageUp / PageDown 阅读并提交高于终端答题区的选项，Cloud 回复在历史加载完成后会就地更新以保持顺序。文档方面，附带的 `openai-docs` skill 补充了迁移到 GPT-6.2 Astra 与 Sol 的说明。Chores 写明 Code Mode 现在对所有宿主连接改走 gRPC，`code_mode_host_grpc` 设置已弃用。完整对照见 rust-v0.171.0...rust-v0.172.0。上述行为以发布说明为准，本机未安装或验证该版本。
