    Hugging Face：用 LoRA 微调 TRELLIS.2 的 3D 生成指南，并提供 Jobs / Docker 脚本

    Hugging Face 的 Pedro Cuenca 于 2026-11-12 发布 TRELLIS.2 微调指南，提供可在 Hugging Face Jobs 或本地 Docker 运行的预处理与训练容器，用来把 TRELLIS.2 适配到自己的 3D 资产。文章说明 TRELLIS 用统一潜空间再解码到所需格式，TRELLIS.2 加强了结构表示，但二者都缺少面向具体品类的简便适配方式。实验用 Google Scanned Objects 中 188 个鞋类物体：作者称预训练结果鞋型大体正确、鞋底不准，因此只微调控制几何的阶段（稀疏结构 Sparse-Structure Flow DiT，以及细节几何 Shape Flow DiT），冻结材质 / 贴图阶段，并用 PEFT 加 LoRA。开始前需要 HF_TOKEN，且账号须已获准使用门控模型 DINOv3；自有数据要先把网格上传到 Hub。预处理容器用无头 Blender 为每个物体渲染 16 个视角，作者称 188 个物体在 a100-large 上大约 1 小时。镜像为 cr.hf.co/suvadityamuk/trellis2-finetuning-prep:latest 与 cr.hf.co/suvadityamuk/trellis2-finetuning-train:latest。文中在 9 个留出物体上给出对比：带鞋类适配器后面的平均 F-score 从 0.276 升到 0.803，Chamfer 距离从 0.174 降到 0.033，法线一致性从 0.530 升到 0.804，且 9 个物体的 F-score 均更好——这是文章自己的实验结果，本机未复现。训练好的适配器发布在 suvadityamuk/trellis-2-finetune-gso。文末把 Pixal3D、UniLat3D 以及 HunyuanWorld 2.0、NVIDIA Lyra 2.0 等列为后续可能方向，并非本次实验范围。

    Unity：6.7 将弃用烘焙遮挡剔除，并说明 GPU / 小网格剔除的现状与后续方向

    Unity 图形团队工作人员 ElaineK 于 2026-11-09（UTC 09:41）在官方论坛发帖，说明剔除工作的现状与后续方向，并写明当前重点是先改进已上线能力、再加新功能。烘焙遮挡剔除（基于 Umbra 中间件）将在 Unity 6.7 弃用：团队表示这是较旧技术，无法再更新或带到新平台，且与 GPU-driven 路径配合不佳——经 GPU Resident Drawer 绘制的物体可被烘焙数据隐藏，但不能作为遮挡物去隐藏其他物体，检测也更低效；烘焙之后新创建的物体同样不能遮挡其他物体。新项目不再显示烘焙遮挡剔除 UI，已启用 Umbra 的项目会在 Occlusion Culling 窗口看到弃用提示（原文写作 depreciation）；既有项目在 6.7 生命周期内仍可继续使用，文档也会加上弃用说明。GPU 遮挡剔除仍在开发中：适用于经 GPU Resident Drawer 渲染的内容，在极密实例化场景表现很好，但在高度独特内容上可见性检测的开销可能大于收益，因此除非场景实例非常密集，一般建议先关掉；团队也在改进 GPU Resident Drawer，让 GPU 遮挡剔除能覆盖更多内容。小网格剔除已在 Unity 6.6 通过 GPU Resident Drawer 提供：可设屏幕尺寸阈值，过小的物体不再提交渲染，阴影投射物也可按 cascade 设各自阈值。文中还列出仍在调研或规划、尚未作为已交付功能保证的方向：更多 GPU-driven 剔除、扩大移动端 GPU 兼容、面向移动端架构而非从桌面移植的遮挡剔除、阴影灯在无相关变化时跳过冗余剔除、分屏/小地图/瞄准镜/镜像等多摄像机以及 XR 中几乎完全重叠的视图共享剔除工作，以及让剔除可脚本化（按相机控制，或插入自定义遮挡/预计算可见性等逻辑）。这些是团队计划与向开发者征询，不是已经发布的能力。本机未在 Unity 6.6/6.7 中实测上述选项。

    War Thunder Eagle’s Shadow 新渲染（其二）：局部色调映射、天空遮挡与粗糙金属 BRDF

    Gaijin 于 2026-11-11 发布 Eagle’s Shadow 新渲染系列第二篇开发日志，介绍光照、阴影与金属反射方面的改动，并配有新旧对比图。此前全屏只用一个曝光值；现在的局部色调映射会把画面各区域亮度与整帧比较，较暗区域轻轻提亮、较亮区域稍压，并加一点局部对比以免发平。每个区域的调整被限制在上下各一档（one stop），且区域亮度会跨帧跟踪并跟随相机和移动物体，避免转头或车辆穿过亮区时曝光跳动。文中写局部色调映射可用于所有抗锯齿模式；Max 与 Movie 画质预设默认开启，其他预设需在图形设置的 Render 栏手动打开。天空遮挡方面，环境光遮蔽此前假定周围光照均匀、未考虑开阔天空下大部分光来自上半球；现在会区分物体是否在建筑内：室外天空遮挡最强，室内稍软，使房间顶部更暗、窗口附近更亮。显示曲线在把 HDR 结果转到屏幕颜色时做了调整：最深阴影和偏低中间调被抬高以保留细节，偏高中间调对比稍增，纯白保持纯白；适用于所有画质预设和所有平台的标准动态范围输出，HDR 输出不变。金属与反射方面，团队称原 BRDF 未计入粗糙表面在锐角下的多次反弹，粗糙金属和刮痕漆面会因此损失最多一半的反射光，现已补回，坦克装甲或飞机蒙皮等粗糙金属在低角度会更亮；还修复了阳光阴影里表面反射偏暗的问题，使低角度的地面/道路反射天空和墙壁而不是自身，并让潮湿与积雪表面的反射按文中所说正确工作。文中称显示曲线调整和反射修复「几乎不占用系统资源 / 没有性能开销」，这是开发商自己的说明，本机未实测。相对本站 11-10 收录的同一更新 DLSS 5 访谈，这篇写的是色调映射与材质反射，不是超分。

Blender 5.3：原生 3D Gaussian Splats、视口 DLSS 4.5 降噪与可选项目系统

Blender Foundation 于 2026-11-10 发布 5.3.0 正式版（官网发布页与新闻稿均写 Initial release / November 10th, 2026）。相对本站 11-10 收录的 Cycles RC 说明，这是已出包的稳定版介绍，并补上 3DGS、EEVEE 与工作流改动。头牌是原生 3D Gaussian Splats：可从 PLY、SPZ 和 glTF 导入为点云，用 Geometry Nodes 处理，并在 Workbench、EEVEE 与 Cycles 中渲染；默认用自发光着色，文档称把 Emission 换成 Diffuse 等硬表面 BSDF 可做「初步」的可重打光，同时写明性能仍在优化，且因多数制作工具用 sRGB、Blender 用线性色彩，低透明度、高辐射区域可能出现不准。视口新增 DLSS 4.5 Ray Reconstruction 降噪器，通过超分并复用先前帧样本；位于渲染属性 Sampling 的 Denoise 面板，需要 NVIDIA 驱动 620 或更新；并写明对运行 Windows 11 的 NVIDIA RTX Spark 提供原生支持（含内存优化）。Cycles 方面 Principled BSDF 增加色散（对应 OpenPBR v1.1.1），Glass BSDF 与 Principled 透射分量支持粗糙度各向异性。EEVEE 新增 Material Lighting 节点（Light Accumulation / Light Info / Light Evaluation / Shadow Raycast 等），并支持全景相机；当前实现尚不支持景深、光线追踪，以及视口里体积的时间重投影。另外还有可选的项目系统（项目级资源库与色彩管理等）、把 Asset Library 作为扩展分享、合成器效果栈，以及视频序列编辑器的 ripple 编辑框架、重写的 Blade 工具和初步 OpenTimelineIO 支持。同期新闻稿还写 Vulkan 现为 Windows（ARM 除外）与 Linux 的默认后端，Workbench 可在 Metal 与 Vulkan 上使用硬件光线追踪阴影；本条链接是功能介绍页，该后端变化以新闻稿为准。本机未安装 5.3.0 验证。

Epic 文档：Lumen World Cache——运行时路径追踪缓存，可替代网格 Cards 的 Surface Cache

5.9 新文档介绍 Lumen World Cache：默认关闭，仅在 Lumen 走硬件光追时生效；开启后该视图完全替换 Surface Cache（不再捕获/照明/驻留 mesh cards）。缓存按距相机的稀疏世界空间格子存储（默认约 10 米处每格约 25.6 cm，并按主朝向分条目），每帧从屏幕每 8×8 像素块随机取一点、最多 3 次反弹填入，格子最多平均 16 帧，64 帧未命中则回收。开启方式是在 DefaultEngine.ini 写入 r.Lumen.WorldCache.Supported=1 并重启；还要求 Hardware Ray Tracing Mode 为 Full 或 Simplified Material（Inline 不可用），且 r.Lumen.WorldCache.Allowed 保持开启（默认真，可作分档开关而不重启）。文档列明限制：软件光追仍走 Surface Cache；半透明不入库；暂不支持 Water、光追半透明、植被/次表面透射，以及 Far Field。GPU 耗时可在 stat gpu 的 LumenWorldCache 项查看，默认可走 async compute。

这篇 2026-11-05 提交的论文指出，现有前馈 3DGS 通常先由几何基础模型预测深度，再在径向距离归一化（RDNorm，用重建点到参考相机原点的平均径向距离做全局缩放）的坐标系里预测 Gaussian 属性；但相邻 Gaussian 中心间距（Gaussian spacing）仍会随场景尺度和相机配置大幅变化，使相近的局部观察对应不同的尺度监督目标。作者提出 SplatAnything 与 Gaussian Spacing Normalization（GSNorm）：在逐像素预测假设下，局部间距近似为深度除以焦距几何平均，即 d≈D/√(fx fy)，再用所有有效像素的中位数作为场景尺度，把几何、深度和相机平移一并缩放，使该中位数间距为 1。几何由冻结的 WorldMirror 2.0 估计，随后微调 Gaussian Backbone 并用从头训练的 GSHead 预测不透明度、旋转、尺度和球谐系数。为评估跨场景与外推视角，作者建了一套覆盖 ScanNet、NRGBD、DL3DV、Tanks & Temples、Mip-NeRF 360、ETH3D、DTU 的基准，控制输入 4/8/16/32/64 视并强调遮挡感知共视约 0.2–0.6 的外推目标。作者报告在多数设置下优于所列基线，例如无位姿时 ScanNet 上 DISTS/LPIPS 为 0.184/0.207（Mirror2-GS 为 0.193/0.222），DTU 上为 0.229/0.483（Mirror2-GS 为 0.347/0.617）；同一架构消融里 4 视 GSNorm 为 0.198/0.245，对照 RDNorm 的 0.223/0.278。训练为 2 万步、64 张 NVIDIA H20，输入 4–32 视、分辨率 504–1024。文中也写明：方法依赖几何先验，在极稀疏或几何不可靠输入上可能下降，且主要重建输入可见区域。项目页为 https://zju3dv.github.io/SplatAnything/ 。以上均为论文实验与作者结论，本机未复现。

提问方沿用传统 Static Mesh 的做法，希望 Nanite 也能按距离换成更简单的材质（近处多层细节法线、远处烘焙贴图），以降低显存和着色成本，并询问 UE 5.8 是否已支持；他们的场景有大量不复用的独特道具。Epic 的 Tim Stullich 答复：目前没有计划支持按距离切换的材质 LOD。Nanite 通常靠 shade binning 降低材质求值成本；引擎虽有 Nanite Override Materials，但不一定覆盖这种「近复杂、远烘焙」需求。对方追问后他补充：团队讨论过给 Nanite 加材质 LOD，主要顾虑是材质变体和 shading bin 数量会变得难管理；目前正在减少变体，已把需求提给开发组评估。8 月 26 日他改口得更明确：按距离做材质 LOD 与 Nanite 的演进方向相反，短期内不太可能加入，因为额外材质 LOD 会制造更多 shading bin，而这正是 Nanite 的主要瓶颈之一。可落地的替代是：若要在 HLOD 上做材质 LOD 链，给网格勾选 Disallow Nanite，运行时退回 Fallback，才能沿用传统材质 LOD；另外可调 WPO Disable Distance 与 Pixel Programmable Disable Distance，让远距实例退回更便宜的光栅——他称这往往比材质 LOD 更影响 Nanite 性能。对于独特道具过多，他建议先复用和实例化。Nanite Material Cache 仍是实验特性、变动频繁，他不建议按项目周期贸然启用。提问方认为 HLOD 不够用，因为 ISM/HISM 只能共用同一套材质。

AffineGS: Unlocking Accurate Geometry in 3DGS via Spatially Varying Affine Rectification

深度引导的 3DGS 常用单目深度先验，并假设预测视差可以用一次全局 scale-and-shift 对齐到度量深度。这篇 2026-11-05 提交的论文指出，Depth-Anything-V2、MoGe、Metric3D-V2 等现代单目网络会呈现区域相关、分段线性的畸变：在 MuSHRoom 与 ScanNet++ 上，残差阈值 0.02 时全局仿射（K=1）的 inlier 大约只有 58.9% / 58.6%，而分成 3 或 5 个局部线性区域时 inlier 分别升到约 84.9% / 84.6% 与 92.7% / 91.8%。AffineGS 不改 3DGS 表示，而是用渲染深度与单目视差的空间梯度估计局部尺度场，再用视差引导的 Guided Filter 做边缘感知平滑，并加上法线感知的梯度域正则和一次全局最小二乘重对齐。实验在单张 RTX 3090 上训练 3 万步。NeRF-LLFF 稀疏视角（2/3/4/5 张训练图，10 个随机种子平均）上，平均 PSNR 为 18.79 / 20.95 / 22.37 / 23.32，相对当时最强基线 DRGS 的 17.31 / 18.75 / 20.06 / 20.78。MuSHRoom 上无传感器深度的 Ours 新视角 PSNR 为 24.49 / 22.07（两个测试划分），接近带真值深度的 DN-Splatter（24.58 / 21.89），Abs Rel 为 0.0551 / 0.0490，而把同一单目先验做全局对齐的 DN-Splatter (Monodepth) 为 0.3542 / 0.3669；网格 F-score 为 0.7097 对 0.2765。ScanNet++ 上无传感器方法里法线一致性最高，但若干基线的 Chamfer / F-score 更好；文中也写明 kokko、sauna 等场景需要减弱损失权重，且结果仍没有绝对物理尺度。项目页为 https://eldentse.github.io/AffineGS/ 。以上均为论文实验，本机未复现。

论坛：Nanite Voxelize 下加大阴影 LOD Bias 反而更贵——Epic 解释原因并给出 VSM 杠杆

提问方在 5.7.2 用 Landscape + PCG Nanite 植被 + 单盏方向光测 VSM：Shape Preservation 设为 Voxelize，并关掉 VSM 缓存测最坏情况，阴影深度大约 5.8 ms。他们增大 r.Shadow.NaniteLODBias 后阴影成本不降反升，直到 bias 超过 4 才开始下降；同一场景改用 Preserve Area 或 None 时，加大 bias 则会按预期降成本。Epic 的 Ola.Olsson2 认为这并不意外：体素路径被高度优化成一种 LOD 技术，放大时仍走三角形；无偏差时遇到的是亚像素体素，采样很便宜。体素变大后会变成盒子，需要另一套算法（类似大三角形走硬件光栅），而体素没有这条路径，因此加大 bias 很难省钱。他们内部测试里，bias=0 时实际光栅会下降，但 cluster culling 等上升，所以通常把 bias 留在 1 更划算，也有利于仍走三角形的部分。其他可试的杠杆：若几乎没有大气效果，关掉 r.Shadow.Virtual.MarkCoarsePagesDirectional 往往收益明显（他称这仍是 VSM 的弱点）；确认 r.Shadow.Virtual.UseReceiverMaskDirectional 在 5.7 默认开启；测「无缓存」时应用 r.Shadow.Virtual.Cache.ForceInvalidateDirectional，他并不完全确定只设 r.Shadow.Virtual.Cache=0 效果相同（尤其 HZB）。对 5.7 的体素+VSM，他建议密林优先让缓存生效；5.8 则有实验性 r.Shadow.Virtual.PrefilteredDistant，可把远景几何画得更低分辨率，对动态太阳下的密林帮助很大，但这条路径完全不走缓存，当时仍高度实验。

提问方在默认开放世界地图上用 Megatree 做实验：用一组 PCG Volume 在地形上生成树木，树木是 Instanced Skeletal Mesh，走全局植被 Actor 做动画，并启用 Nanite voxelization。目标是借助 World Partition，让远距树木变成 HLOD。给 PCG Volume 指定 HLOD Layer 并构建后，「Show HLOD colorization」里远景地形会变蓝，树木却仍是原色。卸载整张地图后仍能选中各片森林的 HLOD，说明代理确实生成了；但卸载后飞近树木又会开始动画，看起来像已被加载。约 12.5 万实例在其 5080 上也不划算，且加上 HLOD 后没有看到性能收益。提问方随后自行复查（无 Epic 跟帖）：当时 HLOD 层类型是 Instancing，系统只是按格子把 PCG 实例合成更大块，代理是生效的——改了树种却不重建 HLOD 再进游戏，远景仍是旧树。因此他认为 HLOD 着色可视化对 Nanite 体素资产不起作用。把层类型改成 Instancing 以外的任何方式都会构建失败，体素化植被似乎只能走 Instancing HLOD。HLOD 虽然减少了 Nanite primitive 数量，但收益不明显，用更大的 PCG Volume 也能得到类似结果；更复杂的场景里，给植被加 HLOD 或许才更有意义。这是提问方的自查结论，不是 Epic 官方确认，可与「Nanite Foliage 如何进入 Instancing HLOD」那条互相参照。

Epic 文档：Runtime Virtual Texturing——写入/采样、流送低 mip 与每帧上传预算

UE 5.8 官方说明如何用 Runtime Virtual Texture（RVT）在运行时由 GPU 按需生成纹素，并把大范围着色结果缓存下来，适合带贴花感材质和样条的地形着色。流程是：在内容浏览器创建 RVT 资产，向关卡放入 Runtime Virtual Texture Volume，让材质写入并采样该资产，再把图元或 Landscape 指派给它。每个 Volume 只绑定一份 RVT 资产；场景组件可以写入多份。材质须使用 Virtual Texture 域或 RVT 相关表达式。资产可选多种 Material Type，并对应不同压缩：仅 Base Color（BC1），Base Color/Normal/Roughness/Specular（BC3+BC3），YCoCg Base Color、Normal、Specular（BC3+BC5+BC1）以及带 Mask、World Height（R16_UNORM）、Displacement（BC4）、Mask4（BC3）等变体。文档建议做法线时写入世界空间，以便多个图元混合。Volume 应用 Transform from Bounds / Set Bounds 套住地形或相关组件，并以 Volume 负 Z 方向做正交投影。写入与采样靠 Runtime Virtual Texture Output / Sample / Sample Parameter；也可用 Runtime Virtual Texture Replace、Virtual Texture Feature Switch，以及 View Property 里的 Virtual Texture Output Level / Derivative / Max Level，按 mip 近似做与相机无关的「距离」着色。适合写入的是 Landscape、Landscape Spline、静态网格、ISM 和做贴花散射的植被实例；骨骼网格、可移动或动画网格不合适，因为 RVT 是着色缓存，不会每帧完整更新，写入对象应为 Static。Draw in Main Pass 可选 Never、From Virtual Texture 或 Always：只写入 RVT 的贴花平面在无虚拟纹理支持时应选 Never；地形则应 Always，以便同时写入并采样。仅写入 RVT 的图元应手动关掉碰撞。图元可调 Virtual Texture LOD Bias、Skip Mips、Min Coverage；Landscape 的 Virtual Texture Num LODs 为 0 时每个组件以单四边形写入，对 GPU 最省，需要高频顶点插值时再提高。Volume 还可设置 Streaming Levels 并 Build，生成 Virtual Texture Builder，把低 mip 交给 Streaming Virtual Texture；编辑器默认仍看运行时 RVT，勾选 Use Streaming Low Mips in Editor 才预览流送数据，Build Debug 会给流送 mip 染色。RVT 设置改动后若未重建，关联 SVT 会失效并在 Map Check 中报警。调试可用 stat virtualtexturing、stat virtualtexturememory，以及 r.VT.Flush、r.VT.MaxUploadsPerFrame（编辑器默认 64、游戏默认 8）、r.VT.RVT.TileCountBias、r.VT.PoolSizeScale 等。限制包括：顶点着色器采样没有 GPU feedback；填充 RVT 的材质不能再采样虚拟纹理；普通流送纹理写入 RVT 可能在未完全流入时留下问题；ISM 即使勾了 Use GPU Lod Selection，RVT 也不走 CPU/GPU 实例剔除与 LOD 选择。
