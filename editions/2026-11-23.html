论坛：UE 5.8 在 GI 可扩展性为 Low 或 Medium 时，游戏进程里 Lumen 漫反射会变成 0

作者 @FrankieDcreator 报告：在源码构建的 UE 5.8（Windows 11、RTX 5070）上，把 GI 可扩展性设为 Low 或 Medium 后，打包或游戏进程里 Lumen 漫反射为 0，Lumen GI 消失；提高到更高品质后，Lumen GI 会恢复。他在 2026-11-15 用一张诊断关卡隔离了这个问题，并询问这是否为 5.8 的预期可扩展性行为，以及在不把品质强制提到 Epic 或 Cinematic 的前提下，怎样配置才能让打包/游戏运行仍保留 Lumen GI。发帖时还没有回复，帖中也没有给出已验证的变通或官方说明。

    论坛：正交相机 + VSM 切图时，渲染线程会对正在销毁的世界做物理查询（已验证关掉 r.Ortho.VSM.RayCastViewOrigin）

    作者 @AlexandreStAmant 报告：在没有 ViewTarget 的正交相机（例如独立 CameraActor）上启用 Virtual Shadow Maps 和可移动方向光时，FVirtualShadowMapClipmap 构造函数会在渲染任务 FGatherShadowPrimitivesPrepareTask 里调用 UWorld::LineTraceSingleByObjectType()，由默认开启的 r.Ortho.VSM.RayCastViewOrigin 控制。这条物理查询没有和游戏线程同步。切图时游戏线程会在 LoadMap → TrimMemory → GC → UWorld::FinishDestroy 中销毁旧世界和 FChaosScene，渲染任务仍可能在查询它。他们遇到的崩溃是：渲染工作线程在场景查询里拿到 Chaos 求解器的外部数据读锁后进入崩溃处理却仍持有该锁，游戏线程随后销毁求解器并触发 Assertion failed: !IsLocked()（“Destroying a lock that is still held!”）。作者写这段代码在 5.6、5.7、5.8 和当时的 ue5-main 中都还在（VirtualShadowMapClipmap.cpp，5.8 约第 283 行），CVar 默认仍为 true。复现条件是场景里有正在模拟的刚体，并在打包的 Win64/D3D12 Development 构建里循环 OpenLevel；他们大约每 50 次切图出现一次。建议的修复是把视点估计改到游戏线程再经 FSceneView 传入，或至少在修复前把该 CVar 默认改为 false。已验证的变通是在 [SystemSettings] 里设置 r.Ortho.VSM.RayCastViewOrigin=0，以关闭这条渲染侧射线。发帖时还没有 Epic 答复。

  2. 图形渲染UE 日报03

    论坛：开启硬件光追后，切图时 ComputeViewExtension::GetFlags() 会在渲染线程空解引用 UWorld（含补丁建议）

    同一作者 @AlexandreStAmant 另报：在开启 r.RayTracing 且启用 ComputeFramework 插件的 5.8.2 源码构建（Win64/D3D12，打包 Development）里，切图时渲染线程会在 FComputeViewExtension::GetFlags() 里对空 UWorld 解引用，出现读取地址 0x258 的访问违例。原因是该函数先用 TWeakObjectPtr 的 IsValid() 检查世界，再用 operator-> 取 Scene；这两次会分别解析弱指针。LoadMap 时游戏线程可能正在销毁旧世界，两次解析之间世界失效，第二次 Get() 返回空指针后访问 WorldPtr->Scene 就会崩溃。PostTLASBuild_RenderThread() 也用了同样写法。作者还指出可变成员 ComputeWorkers 被当作临时缓冲，多个 view family 并发调用时并不线程安全。他认为这条路径来自 2026-03-26 的提交 344f81b（“[PCG] Add engine infrastructure for PCG GPU inline ray tracing”）。复现是在三张小地图之间循环 OpenLevel，大约每 3–4 秒一次；他们跑了约 9 小时、700 次 LoadMap 后才撞上，竞争窗口很窄。建议的修复是不要在渲染线程碰 UWorld，改为把 FSceneInterface* 传给扩展并缓存，并用局部数组替换那个可变成员。变通是设 r.RayTracing=False，因为 FDeferredShadingSceneRenderer 里两处 GetFlags() 调用都在 IsRayTracingEnabled() 之后。发帖时还没有 Epic 答复。

Epic：UE6（含 Early Access）将不含 Blueprints 与 Actor 玩法框架，改用 Verse 与 Scene Graph

Epic Games 开发执行副总裁 Marcus Wassmer 于 2026-11-20 在 Unreal Engine 官网发文《An update on Blueprints and the path to UE6》（页面显示 November 20, 2026；官方 RSS 标注 published 为 2026-11-20 00:00:00 GMT）。文章写明：UE6（包括 UE6 Early Access）将不包含 Blueprints 与 Actor Gameplay Framework，玩法将在 Verse 和新的 Scene Graph 框架上构建。作者回顾，今年 6 月曾表示 Blueprints 与 Actor 会在 UE6 Early Access 和 6.0 中并存，以便 UE5 项目在 Scene Graph 成熟时逐步升级；此次改口的理由是“近期 AI 能力的进展”。文中写到，Epic 预期 AI 将大幅帮助把 UE5 项目转到 UE6，“哪怕还不能让这一过程完全自动”，并称这样可以按时（或更早）交付 UE6，同时满足其设计目标：新的数据模型、Verse 优先的架构、模块化，以及 AI 可操作性。上述“大幅帮助 / 完全自动 / 按时或更早交付”均为官方预期，并非已完成的迁移结果。关于成本，文章引用 Epoch AI 的“任务成本同比下降 13 倍”并认为趋势会持续甚至加速，从而在 UE 6.0 面世时转换成本会较为有限；该倍数与成本判断均来自文中引用和推测，本栏未核对 Epoch AI 原文。Fortnite 方面，作者称大约两周前用 AI 尝试把 Battle Royale 的全部 Blueprint 转成 Verse：该工作原先预计要数年，但现在已有一个可运行的 Fortnite 原型，在移植超过 20,000 个 Blueprint 后约有 300 万行 Verse 代码；团队仍在迭代，以验证性能、内存占用和架构。这是 Epic 自己的实验陈述，本栏未见到独立复现。文章明确：是否继续把项目留在 UE5 由开发者自己决定，不必等到 UE6 才能使用更多 AI 工具。Epic 已开始把为 UE6 做的 AI 工具带回 UE5，首先出现在 UE 5.9 MegaJam Preview，并列了四项：扩大的编辑器 Python 脚本访问、MCP 改进（把首选模型接到编辑器并直接在项目里工作）、把 Web 作为目标平台、以及 Unreal Canvas（生成资产，并把编辑器内容、引用和反馈并排、保持可更新和可控）。文中还称 UE 5.9 的相当一部分（包括大部分 Web 平台工作）是用 AI agent 做的，并表示在开发 UE6 期间会继续针对 UE5 做有针对性的功能、修复和支持。5.9 预览的渲染与动画更新见文内链到的发行说明；本栏未安装或验证 5.9 Preview。

论坛：UE 5.7.4 / 5.8.4 里 AlphaHoldout 会留下黑色剪影，分离半透明并给接收材质加微弱 IOR 后可挖洞

作者 @caste117 想在编辑器视口里用 AlphaHoldout 给半透明平面挖洞，直接看到后面的不透明墙和地面。他先在 UE 5.7.4 遇到问题，随后在 5.8.4、Deferred、DX12、SM6 上复现。测试场景是一块橙色半透明平面前放一个 AlphaHoldout 立方体，平面后再放不透明墙；两种材质都是 Unlit、Before DOF、Opacity = 1，平面的 Translucency Sort Priority 为 0、立方体为 1，并且已打开 Alpha Output 与 Support Primitive Alpha Holdout (Deferred)。当平面的 Refraction Method 为 None 时，立方体只会留下黑色剪影。他在 5.8.4 上把平面的 Refraction Method 改成 Index Of Refraction、IOR 设为 1.01，并在 Output Log 执行 r.SeparateTranslucency 1 与 r.Translucency.StandardSeparated 1 后，可以看到墙和地面从挖洞处透出；若把 r.Translucency.StandardSeparated 改回 0，或把折射方法改回 None，黑色剪影会回来。文档里的 AlphaHoldout 小节只写了背景应从洞中透出，没有提到这两条控制台变量或 distortion pass。作者还指向更早的帖子：该效果在 5.4 可用，5.5 / 5.6 已出现同样的黑色剪影。他询问版本之间行为是否改过，以及在接收材质保持 Refraction Method = None 时有没有官方支持的做法，因为并不需要折射，也不想只为挖洞多开一个渲染通道。发帖时还没有回复。

AGSR：用收缩投影协方差的多孔径渲染，给预训练 3DGS 做推理时超分（论文）

Ayman Alkhateeb、Hadi Amirpour、Christian Timmerer（Alpen-Adria-Universität Klagenfurt）的论文于 2026-11-19 提交 arXiv（编号 2611.25934）。作者认为 3D Gaussian Splatting 的光栅化会通过每个图元的投影协方差衰减细尺度结构，并在推理时收缩这些投影协方差，以缓解有限高斯足迹带来的等效带宽限制，从而得到多孔径渲染。据此提出 AGSR（Aperture-Guided Super-Resolution）：在推理阶段逐步融合多孔径渲染，用不确定性引导的特征聚合，以及透射率、深度等几何条件；它作为插件增强已训练好的 3DGS 模型，底层高斯表示保持冻结。实验在 Mip-NeRF 360 上进行，并对训练图像按 tf∈{2,4,8} 下采样得到不同质量的 3DGS，再评估 2× 与 4× 超分。论文报告：在 2×、tf=8 时，AGSR 相对双三次上采样将 PSNR 提高 1.69 dB、SSIM 提高 0.039，相对直接以目标分辨率光栅化的 Native 3DGS 提高 4.34 dB PSNR（表 II：AGSR 25.49 / 0.764 / 0.349，Bicubic 23.80 / 0.725 / 0.358，Native 21.15 / 0.631 / 0.437）。在 4×、tf=8 时，AGSR 的 SSIM 为 0.766、LPIPS 为 0.360。作者也写明：在低退化 tf=2、2× 时，微调后的 SAFMN 在 SSIM（0.830 vs 0.827）和 LPIPS（0.281 vs 0.287）上略优于 AGSR。复杂度方面，网络约 21K–139K 参数；表 I 在 NVIDIA RTX A6000、batch size 1、目标 Full HD（含 3DGS 光栅化与网络推理）上测得：2× 在 3 个融合阶段时 FP32/FP16 为 22/27 FPS，4× 因输入分辨率更低，3 阶段为 64/76 FPS。这些指标均为论文实验数据，本机未复现。arXiv 摘要页未见 Comments 字段，也未见官方代码仓库或项目主页。

论坛：开启 Nanite Tessellation 后，硬件光追阴影对不齐置换后的表面（社区解释原因）

作者 @HN1214 报告：在 UE 5.6 / 5.8 上使用 Lumen 与硬件光线追踪时，打开 Nanite Tessellation 后能看到网格上的置换，但光线追踪阴影对不齐置换后的表面。这个问题在侧光特写镜头里尤其明显，对影视镜头很关键。他询问更新的引擎版本是否已修复，若仍在开发则目标版本是什么。次日 @glitchered 给出社区技术解释（并非 Epic 官方答复）：Nanite 置换是实时变换的可视几何，而光线追踪依赖放进加速结构（BVH）里、预先变换好的静态或“动态”几何；Nanite 细节太多，难以即时重建 BVH，因此会使用更低分辨率的代理 BVH，这份代理不会为虚拟置换后的几何计算正确阴影，所以对不齐。答复认为这需要较长时间才能解决，帖中没有给出已验证的变通，也没有官方修复或目标版本。

Codex CLI 0.171.0：默认打开 TUI workspace，目录加入 GPT-6.2 Sol / Astra，并支持远程 exec

OpenAI 在 GitHub 发布了 Codex CLI 0.171.0（标签 rust-v0.171.0，发布时间 2026-11-20T00:44:47Z）。新功能包括：把 GPT-6.2 Sol 与 Astra 加入模型目录，并以 Sol 作为目录的默认选项；默认启用 TUI workspace，可在主对话旁提供可搜索的文档预览、图片预览和子代理 transcripts；为非 Vim 的提示编辑器增加可配置的撤销/重做快捷键，并可恢复附件和大段粘贴；新增 `codex exec --remote`，可在已有的 app server 上启动或恢复非交互会话；TUI 中新增 `/rc` 与 `/remote`，用于管理本机远程控制并显示设备配对码；在启用 `tui_extensions_statusline` 时，可通过 `/statusline` 选择或编写自定义 MCP 状态行。修复方面，发布说明列出：切换或恢复会话时保留草稿、排队的后续输入和被打断的输入及其原线程；更换工作目录时保留权限配置；避免迟到的完成事件取消较新一轮的审批；在引导进行中的回合时保留聚合 diff 中的先前提交编辑；修复滚动插入杂字符、输入光标跳动，以及用过期终端尺寸重绘；并修复企业 MCP 登录在身份提供方只签发不含 refresh token 的 ID token 时失败的问题。发布说明还提到将源码构建与发布工具链更新到 Rust 1.99.1。完整变更见 rust-v0.170.0...rust-v0.171.0。上述行为以发布说明为准，本机未安装或验证该版本。升级后 TUI workspace 会变为默认布局，而不只是给曾经手动开启的人使用。

Hugging Face：为特定 agent 框架训练 LoRA harness adapter，提升准确率并减少工具调用

Lewis Tunstall 于 2026-11-20 在 Hugging Face 博客发布《Introducing harness adapters: adapt your favorite model to your harness to improve performance and cost》。文章的核心做法是：冻结基座模型，在目标 agent 框架（harness）内部用强化学习训练定制 LoRA，使模型适应该框架及其任务分布。作者为 Qwen3.8-27B 分别给 pi、Hermes Agent 和 OpenCode 训练了一个 adapter，训练与 rollout 在 Hugging Face Jobs 上用 TRL 的 `AsyncGRPOTrainer`、OpenEnv 和 Harbor 完成；最终镜像里的框架版本写明为 Pi 1.5.2、OpenCode 2.2.7、Hermes Agent v0.22.6。文首示例称，Qwen3.8-27B 在 pi 框架下的 Terminal-Bench 2.1 分数为 39%、平均每任务约 2.9K token，加上 adapter 后为 55% pass@1、平均约 1.5K token，作者将其主要归因于更少推理、更少工具调用和更高的一次成功率。后文还报告：三个专用 adapter 在各自框架下、两个基准上都超过基座模型。在 SWE-bench Pro（hard 51）上，pi 从 39.2% 升到 64.7%（+25.5 分：新解 15 题、丢失 2 题，p=0.002），Hermes 从 29.4% 升到 43.1%。在两边都能解出的任务上，adapter 在 SWE-bench Pro 上少 56%–72% 的工具调用，在 Terminal-Bench 2.1 上少 53%–70%。三个 LoRA 还被合并成一个可在 pi、Hermes Agent 与 OpenCode 下不变运行的 super-adapter。作者同时做了交叉和域外检查：例如把 pi 的 adapter 放到 OpenCode / Hermes 下评估，以及在 AutomationBench 自带 agent loop（不是这三套框架）上跑 300 个任务，结果显示 adapter 与基座接近，差异被作者视为噪声范围内。adapter、GGUF、RL 任务和 safeagents 插件可通过文中的 Hugging Face collection 浏览。上述分数与效率数字均为文章报告的实验结果，本机未复现训练或评测。

为什么有用

若你已经选定了 Pi、OpenCode 或 Hermes 一类 agent 框架，又想在不换基座模型的前提下提高正确率、减少工具调用和 token，这篇给出可复用的 RL-LoRA 配方和公开产物；成效以作者在其任务分布上的评测为准，换框架或换任务时需要自己验证。

阅读 https://huggingface.co/blog/harness-adapters-at-scale，再打开文中的 Hugging Face collection 查看各框架的 adapter、GGUF 和 RL 任务。若要复现训练，按文中 TRL `AsyncGRPOTrainer`、OpenEnv 与 Harbor 的 Jobs 流程进行。本机未训练或评测这些 adapter。
