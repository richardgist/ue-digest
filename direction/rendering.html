论坛：Nanite Landscape 组件数、Tessellation 与 VisBuffer 空 bin 开销（Epic 答复）

Epic 确认：每个 Landscape component 因独立 weightmap 对应独立材质实例，从而占独立 shading/raster bin；开 Tessellation 后无法走 fixed-function bin，空 ExecuteIndirect 会拖 VisBuffer（低端更明显）。默认世界删到 1 个 section 时 NaniteStats 常见约 42 bins（含 TwoPass）；可试 r.Nanite.Culling.TwoPass 0 便于读数，Tessellation 可试 r.Nanite.DicingRate 3–4。一个 Nanite Landscape component 最多挂 64 mesh sections；更大 component 减少 MIC/bin，但图层更杂、材质更贵。Fortnite 示例约 4 components/proxy、不走 Landscape HLOD。内存上 Nanite 与非 Nanite 两套数据并存；碰撞/导航/Lumen card/DF 仍走标准 Landscape。

UE 5.8：Geometry and world readiness——Nanite 池、WP 就绪门与传送预加载

把「几何已加载」与「可进入」拆开：Nanite 用 StreamingPoolSize 在内存与 IO/解压之间权衡，过小即使静态视口也会 thrash，改前先看 Nanite Streaming Geometry 与 NaniteStats，并单独核验包体/存储。World Partition 格子加载只是一层，就绪门还应覆盖 collision/navigation、资产与 bundle、贴图/Nanite/VT 质量下限、渲染/物理组件注册、首帧可见 PSO、玩法初始化。预加载超前距离按最大接近速度 × 最差就绪延迟 + 余量估算；传送用临时目的地 streaming source，等 WP subsystem 完成后再过完整就绪门，避免为一条路径全局抬 loading range。

UE 5.8：Texture streaming——先诊断再动 PoolSize

贴图流送调优流程：先 Build Texture Streaming，再用 Primitive Distance / Mesh UV Density / Material Texture Scales / Required Texture Resolution 等视图找坏 bounds、UV 密度、材质缩放或驻留不足；用 stat streaming 记录 Texture/Streaming/Wanted/budget/over-budget/update time，并在目标相机路径上区分临时缓存 mip 与持续需求。给出 PoolSize、FramesForFullUpdate、MaxTempMemoryAllowed、MipBias、UsePerTextureBias、LimitPoolSizeToVRAM 等杠杆；明确 r.TextureStreaming 0、PoolSize 0、UseAllMips、FullyLoadUsedTextures 只作诊断/展示，不是 Shipping 默认解。应先修过期 MI 流送数据、错误 UV 密度、过大 bounds、强制驻留、贴图组与源分辨率，再考虑加大池。
