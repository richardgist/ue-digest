HiGS：用分层 tile 架构加速可微 3D 高斯溅射的渲染与重建（论文）

NVIDIA 研究员的论文 HiGS（Hierarchically Tiled Gaussian Splatting）于 2026-11-24 挂上 arXiv。作者指出，现有 3DGS 管线把同一个屏幕 tile 同时当作分区、光栅化和并行工作的单位，最密的 tile 会拖慢整帧。HiGS 把高斯按粗粒度 macro-tile 分区，在其中的细渲染 tile 上光栅化，并以有界、按深度排序的 batch 作为工作单元，密集区域改发更多 batch，而不是拉长单个单元。同一套 batch 也用于重建：合成提供透射率与颜色，使各 batch 可独立反传；作者还将优化器融合进反向传播，直接更新的参数与动量减半，并推迟当前视图外的外观更新。作者在一块 NVIDIA RTX PRO 6000 Blackwell 上报告：对已公开的 3DGS 预训练模型，Mip-NeRF 360 七个场景的渲染吞吐量为 1080p 2756 FPS、4K 1533 FPS（由表中各场景中位帧时间的均值换算），相对 gsplat 为 5.1× / 5.6×，并快于文中所有已发表对照方法；在 13 个常用场景上，重建比次快方法快 2.3×–3.0×、比 gsplat 快 5.9×–7.3×，显存约为其中最省方法的 1/1.9，数据集平均 PSNR 与对照方法相当，且使用精确的前到后 alpha 合成。附录写明源码将在正式发表后公开。以上数字均为作者评测，本机未复核，目前也未见独立代码仓库。

    论坛：UE 5.8 开启 Substrate 后，Static Switch 经 Reroute 接到材质函数非首个 Substrate 输出时会报 Material information is invalid，Cook 失败

    作者 @Eel_I_Fukunaka 报告：在项目开启 Substrate 的前提下，若材质的 Front Material 由 Static Switch（或 Static Switch Parameter、Quality Switch、Shading Path Switch）驱动，且其中一路输入经过 Named Reroute 或普通 Reroute，再指向材质函数的第 2 个及以后的 Substrate 输出脚，加载时会打出 LogMaterial: Error: Material information is invalid，Cook 以 ExitCode=25（Error_UnknownCookFailure）失败。编辑器视口里该材质仍能编译并正常显示。复现步骤是：做一个多输出材质函数（输出 0、1 为标量，输出 2 为 Substrate Slab BSDF），把 Named Reroute Declaration 接到输出 2，再把该 reroute 的 Usage 接到 Static Switch 的 B，True 侧接任意 Substrate BSDF，最后把 Switch 接到 Front Material；保存后重新打开编辑器或执行 Cook 即可看到错误。作者定位到 UMaterialExpressionStaticSwitch::IsResultSubstrateMaterial 会跟着 reroute 找到材质函数调用，却检查 reroute 自己的 OutputIndex（0）而不是追踪后的 OutputIndex（2），因而把错误的输出脚当成非 Substrate；同一模式还出现在 StaticSwitchParameter、QualitySwitch、ShadingPathSwitch 以及 GatherSubstrateMaterialInfo 里。SubstrateHorizontalMixing 等节点已经使用追踪后的 OutputIndex，因此不受影响。平台写的是 Windows。发帖时还没有 Epic 答复。

    论坛：免费 MIT 许可的 UE 5.9 Substrate 实时衍射光栅（全息箔）材质，已和 Blender Cycles 做逐像素对照

    作者 @zyyyyyc 把 Blender Guru 的 Balanced 衍射光栅着色器移植到 UE 5.9 的 Substrate，并以 MIT 许可开源（仓库 https://github.com/yichenzhu56/DiffractionGrating-UE）。光栅被建成 30 个倾斜各向异性高光瓣（6 个衍射级次 × 5 个波长）；因 Substrate 每像素最多 4 个 closure，推荐的混合材质 M_DiffractionHybrid 把环境部分在材质里对 Sky Light 立方体贴图评估全部 30 瓣（每瓣 5 次采样）并以自发光输出，直接光则用 4 个 Substrate Slab 覆盖 ±1 级次的两组颜色，并带阴影。为避免重复计算，材质 AO=0，且要求后期体积的 Lumen Max Roughness To Trace=0.2（低于默认 SlabRoughness 0.21）。作者用同一张 HDR 探针、三台 Blender 相机对照 Cycles：混合材质的逐像素相对误差为 0.15–0.20，亮度 96–100%，色彩鲜艳度 97–100%，开启 Lumen 时帧间噪声 0.03%。仓库还提供仅 4 个 Slab 的版本（约损失三分之二色彩）和 Unlit 参考版。要求 Windows、DX12、SM6，以及已开启 Adaptive GBuffer、每像素 4 个 closure 的 Substrate；硬件光追仅路径追踪分支需要。作者写明环境部分约每像素 150 次立方体采样，尚未做性能分析，因而并不便宜；路径追踪输出也还未与 Cycles 做数值对照。槽线方向可用 UV、物体轴投影或三平面，网格没有干净 UV 也能用。11 月 25 日作者补充，原先实例上 ColorFilter 贴图不生效的已知问题已在仓库中处理。

作者 @lastchanc3saloon 报告：在 macOS 27.0、Apple Silicon、Metal SM6 上，用 UE 5.8 Launcher 版打出的 Mac Shipping 包（FullscreenMode=WindowedFullscreen）中，一旦窗口变成菜单栏下方的 1920×1050（y=30）而不是 1920×1080 全屏，IOSurface 会以约每秒 6–8 个、每个约 7.5 MB 的速度泄漏（约 3 GB/分钟）；即使窗口回到 1920×1080，泄漏也会持续到进程重启。作者用 footprint <pid> | grep IOSurface 观察，空闲启动时计数是平的；按 Alt+Enter 两次（先窗口再回到全屏）并移动鼠标后，窗口变为 1920×1050，计数开始持续上升，20 分钟后见过 38 GB 的 IOSurface。栈采样显示渲染线程堵在 FMetalViewport::GetDrawableInternal → -[CAMetalLayer nextDrawable] → IOSurfaceCreate。作者怀疑 MetalViewport.cpp 里两处问题：GetDrawableInternal（约第 727 行）在 drawable 尺寸与后台缓冲区不一致时，每次调用都会释放后再取 nextDrawable，导致每帧取出多个未呈现的 drawable；单视图 PresentDrawLayers（约第 1031–1032 行）对 LocalDrawable->retain() 在 Mac 上没有对应释放，因为该对象只在非 Mac 的 presentDrawable 路径里使用。Shipping 包使用 WITH_MULTI_VIEW_SLATE_WINDOW_SUPPORT=0，因此会走到单视图分支。发帖时还没有 Epic 答复。

论坛：UE 5.8.4 的 PCG 运行时 GPU 实例会在全局重建渲染状态时丢失，且不会自动再生

作者 @potrivaev1 报告：在 UE 5.8.4（Linux）上，PCG 以 Generate At Runtime 并在 GPU 上生成的实例只存在于 GPU Scene（UPCGProceduralISMComponent）。一旦发生全局组件渲染状态重建（FGlobalComponentRecreateRenderStateContext，例如用默认选项构造的 FMaterialUpdateContext），这些实例会被清掉，而且 PCG 收不到通知，因而不会再生；相机周围的运行时植被会消失，直到执行 pcg.RuntimeGeneration.Refresh（编辑器菜单 Tools > PCG Framework > Refresh All Runtime Gen Components）。复现是：关卡里放 Landscape 和 PCG Volume（运行时生成、层级网格 32/64/128 m，图为 Generate Landscape Textures → 自定义 HLSL 点生成 → Static Mesh Spawner，在 GPU 上执行），等植被出现后，打开任意材质资源（不必在关卡中使用）并点 Apply，或用 Python 调用 unreal.MaterialEditingLibrary.recompile_material；实例会立刻消失且不再回来。打开 pcg.RuntimeGeneration.EnableDebugging 1 后，重编译之后没有 [RUNTIMEGEN] 日志，说明调度器不知道实例已经没了。作者称 100% 可复现。UPCGProceduralISMComponent::OnRenderStateDirty 已经处理 MarkRenderStateDirty 这条路径（源码注释写明 GPU Scene 里没有显式持久化实例数据），但全局重建路径不会广播 MarkRenderStateDirtyEvent，该处理器不会被调用。作者还观察到冷启动时，每个材质 shader map 加载完成都会触发整次运行时生成重启，根图在前 15–40 秒可执行 10–16 次，并表现为启动阶段植被闪烁。

LMnOP：用 leave-many-out 重要性修剪 3D 高斯溅射，高比例删除后无需微调仍多数指标领先（论文）

MOBILTECH 与庆熙大学作者在 arXiv 发布 LMnOP（提交于 2026-11-23）。文中指出，3DGS 场景常需数百万个高斯，存储与绘制成本高；常见的 leave-one-out 重要性是单独去掉一颗高斯时的损失增量，在高修剪比例下会漏掉“单独看冗余、一起看却必要”的高斯。LMnOP 改为估计 leave-many-out 重要性：其他高斯也被随机去掉时，再去掉某一颗所带来的平均损失增量。作者给出像素颜色在随机删除下的均值与方差的闭式计算，据此近似重要性，而不必抽样删除模式；再按重要性更新每颗高斯的保留概率，最后一次性修剪。三个数据集（Mip-NeRF360、Deep Blending、Tanks & Temples）在 90% 与 99% 删除、且修剪后不微调的对比中，作者报告 LMnOP 在 18 项指标里有 16 项最好；SSIM 与 LPIPS 在全部 13 个场景上都优于 GaussianPOP。两个例外是 90% 删除时 Deep Blending 与 Tanks & Temples 的 PSNR，GaussianPOP 更高（分别为 27.69 对 27.22、20.81 对 20.15）。在 Mip-NeRF360 上，相对 GaussianPOP 的 PSNR 优势从 90% 删除时的 0.45 dB 扩大到 99% 时的 1.15 dB（99% 时 LMnOP 为 16.53 dB，GaussianPOP 为 15.38 dB）。耗时方面，作者在 Mip-NeRF360 上测得 LMnOP 每场景 19.5 分钟（90%）和 17.0 分钟（99%），GaussianPOP 为 0.9 与 0.6 分钟。另用 5,000 步微调 90% 删除后的 Mip-NeRF360 模型后，作者称 LMnOP 在 PSNR、SSIM、LPIPS 上仍最好。以上数字与对比均为论文结果，本机未复现；文中未见官方代码仓库。

论坛：UE 5.8.4 关卡加载后前几帧，Nanite VSM 的 NodeAndClusterCull 会与异步 Lumen 竞态并 GPU hang（先关 r.Lumen.DiffuseIndirect.AsyncCompute 可避免）

作者 @Byykt 报告：在 UE 5.8.4、D3D12/SM6、RTX 4090（驱动 621.24）上，编辑器在关卡加载后的前几帧会出现 DXGI_ERROR_DEVICE_HUNG。NVIDIA Aftermath 指向 Virtual Shadow Map 的 Nanite 剔除着色器 NodeAndClusterCull（偶发 CullPerPageDrawCommandsCs），同时异步计算队列上正在跑 Lumen 漫反射间接光。复现工程只用引擎内容：平坦 Landscape（6 个绘制层）、108 个生成的 Nanite 静态网格、方向光 VSM、天空光，以及一个空的流送子关卡；加载第 0 帧日志里会出现 ULevelStreaming::RequestLevel 刷新异步加载。冷启动编辑器时，原工程约 2/15 次 hang；去掉 Landscape 降到 0/15，去掉空子关卡降到 1/30。已验证的变通是：启动时设 r.Lumen.DiffuseIndirect.AsyncCompute=0，等渲染满 3 帧后再改回 1，结果为 0/30，对照未使用变通时 8/30。作者认为这像是加载后前几帧里，Nanite VSM 剔除与异步 Lumen 之间缺了依赖或同步。发帖时还没有 Epic 答复；作者把它与仍影响 5.8.4、目标修复标为 6.0 的 UE-230827（已被标为 Duplicate）联系起来，并提供了可公开下载的最小复现工程与 Aftermath 附件。这与 11 月 19 日已收录的 MicropolyRasterize hang 不是同一条报告：本次故障着色器是 NodeAndClusterCull，且明确发生在加载后的第 0–2 帧。

Godot 4.8 beta 5：官方称为本周期很可能最后一次 beta，主要修复回归，并修正 MetalFX 时间上采样抖动

Godot 于 2026-11-24 发布 4.8 beta 5（构建自提交 a661dfdbc）。官方写道，距离 beta 4 不到一周就已解决全部剩余发布阻断，并想在进入 Release Candidate 之前再出一次 beta，因此称这是 4.8 周期“很可能最后一次”开发快照。本篇只覆盖 beta 4 到 beta 5 的改动，整体 4.8 新特性仍以 beta 1 介绍为准。亮点多为回归修复，包括：CanvasLayer 编辑器工作区无法切换；进程关闭时 Trail3D 不更新；PulseAudio 上麦克风输入延迟降到与输出相同；C# 翻译插件改为标准注册以免覆盖用户插件；Find in Files 未复制过滤器；脚本编辑器内部类方法的重写指示相对于父类；继续执行时显示 Game dock；镜像名称未被翻译提取脚本拾取；回退了 Linux 上的 Feral GameMode 集成；以及 Metal 上 MetalFX 时间上采样的抖动偏移单位与符号。changelog 写有 32 位贡献者提交了 54 项修复。下载说明中，.NET 构建（mono）的最低支持版本从 .NET 8 改为需要 .NET 10.0 或更新。这是预发布软件，官方仍提醒备份或使用版本控制。本机未安装或验证该快照。

论坛：UE 5.8.4 在 Vulkan 下，32768 宽的 VSM 图集让体素化 Nanite 树丢失投影

作者 @EK_Studio 报告：在 UE 5.8.4 中，开启 Nanite Foliage 与 Virtual Shadow Maps 并保留 VSM cache 时，Shape Preservation 设为 Voxelize 的静态 Nanite 树会在物理 VSM 图集宽为 32768 像素时丢失全部或部分投影；树本身仍可见，同场景里的普通网格投影正常。问题先在 Linux/Vulkan 打包版出现，后又在 Windows/Vulkan 编辑器里复现（Windows 对照硬件为 RTX 4080 Laptop，驱动 610.91）。用 r.DumpRenderTargetPoolMemory 确认 Shadow.Virtual.PhysicalPagePool 为 32768 宽后，整棵树的影子会消失，或相邻几棵树的影子被切成矩形缺口。两次本地运行都使用 256 MiB 的 R32_UINT 池、两层 array；把 Vulkan Profiles 层的 maxImageDimension2D 报成 16384 后，同一容量的池变为 16384×2048，丢失的影子会回来。作者指出 NaniteRasterizer.usf（CL 58902052，约 1279、1309–1313、1688 行）里，GroupSourceLaneAndPixelPos 把 lane 索引、X、Y 分别打进 5、14、13 位，而单页 VSM 路径使用的是物理图集坐标；例如 (16384, 0) 会被解码成 (0, 1)。发帖时还没有 Epic 答复。
