Inkling 2 Mini：可在笔记本上跑的开源权重循环 Transformer，约 20GB

Thinking Machines Lab 于 2026-11-20 发布 Inkling 2 Mini（官网博文；Hugging Face 模型卡同样标注 Date of release: November 20, 2026，许可证 Apache 2.0）。这是一个循环 Transformer：中间层对每个 token 跑三遍。官方写它是 Mixture-of-Experts，总参数 264 亿、激活 34 亿，计入循环后每个 token 的权重激活为 54 亿；权重以 NVFP4 为主、最后四层为 MXFP8，总内存占用约 20GB，官方称可在消费级笔记本和桌面 AI 机器上运行。权重开放，可在 Tinker 上做推理与定制；官方列出的开源推理包括 SGLang、vLLM、Ollama、Unsloth、NVIDIA Dynamo、TokenSpeed 和 Llama App，并提到 SkyRL、Miles、NVIDIA AutoModel 等可做强化学习微调。模型卡还写支持文本与图像输入、上下文最长 100 万 token，并建议 32GB 及以上内存的 Apple Silicon，或 32GB 及以上显存的其他 GPU。官方自称在总参数不到 1000 亿的开源权重模型中，DeepSWE v1.1 为 48.2%、Vals Index v2.2 为 46.5%，并领先同档模型——这是厂商评测，本机未复现。文中 MacBook 上离线写出飞行模拟器的演示属官方宣传，本机未运行该模型。

Hugging Face：为特定 agent 框架训练 LoRA harness adapter，提升准确率并减少工具调用

Lewis Tunstall 于 2026-11-20 在 Hugging Face 博客发布《Introducing harness adapters: adapt your favorite model to your harness to improve performance and cost》。文章的核心做法是：冻结基座模型，在目标 agent 框架（harness）内部用强化学习训练定制 LoRA，使模型适应该框架及其任务分布。作者为 Qwen3.8-27B 分别给 pi、Hermes Agent 和 OpenCode 训练了一个 adapter，训练与 rollout 在 Hugging Face Jobs 上用 TRL 的 `AsyncGRPOTrainer`、OpenEnv 和 Harbor 完成；最终镜像里的框架版本写明为 Pi 1.5.2、OpenCode 2.2.7、Hermes Agent v0.22.6。文首示例称，Qwen3.8-27B 在 pi 框架下的 Terminal-Bench 2.1 分数为 39%、平均每任务约 2.9K token，加上 adapter 后为 55% pass@1、平均约 1.5K token，作者将其主要归因于更少推理、更少工具调用和更高的一次成功率。后文还报告：三个专用 adapter 在各自框架下、两个基准上都超过基座模型。在 SWE-bench Pro（hard 51）上，pi 从 39.2% 升到 64.7%（+25.5 分：新解 15 题、丢失 2 题，p=0.002），Hermes 从 29.4% 升到 43.1%。在两边都能解出的任务上，adapter 在 SWE-bench Pro 上少 56%–72% 的工具调用，在 Terminal-Bench 2.1 上少 53%–70%。三个 LoRA 还被合并成一个可在 pi、Hermes Agent 与 OpenCode 下不变运行的 super-adapter。作者同时做了交叉和域外检查：例如把 pi 的 adapter 放到 OpenCode / Hermes 下评估，以及在 AutomationBench 自带 agent loop（不是这三套框架）上跑 300 个任务，结果显示 adapter 与基座接近，差异被作者视为噪声范围内。adapter、GGUF、RL 任务和 safeagents 插件可通过文中的 Hugging Face collection 浏览。上述分数与效率数字均为文章报告的实验结果，本机未复现训练或评测。

Hugging Face：在 Transformers 里从 SSD 流式加载 MoE 专家，作者称 32 GB 内存可跑约 180B 的 Qwen3.8-Flash-Next

Hugging Face 的 Tarek Ziadé 于 2026-11-18 发文，介绍如何在 Transformers 中只把 MoE 路由选中的专家从 SSD 读入有界缓存，并让缓存对现有 `grouped_mm` 看起来像普通专家库，从而不必为每种模型重写专家矩阵核。实现以 `from_pretrained` 的 `experts_offload` 选项提交为 huggingface/transformers#50717；作者写明该 API 仍在与维护者讨论，量化专家以后也可能改走另一项分层量化方案。针对 Qwen3.8-Flash-Next，文中给出的做法是：专家量化到 3 bit（磁盘约 49 GB，设备上缓存 12 GiB），稠密层用 8 bit（约 5.4 GB），另外约 51 GB 的 n-gram 嵌入表留在磁盘按需读行。作者称加载后约占 18 GiB，6K prompt 峰值 25.4 GiB，在 32 GB 的 Mac 上接近上限。在同一台 M5、相同提示、关闭 thinking / MTP / 推测草稿的设置下，作者报告优化后短解码 13.9 tok/s（Strata 0.1.60 为 14.8，约差 6%），4K prefill 228 tok/s（Strata 220），6K 文档后解码 12.4 tok/s（Strata 13.7）。作者同时写明这个速度对自己使用的编码 agent 仍然太慢，并提醒关闭浏览器等前台占用，否则 macOS 会开始换页。转换脚本与基准细节放在 Space tarekziade/moe-expert-streaming。上述速度、显存与对比数字均为作者自测，本机未转换权重，也未在 Mac 或 GPU 上复现。

Claude Code 团队谈验证：用端到端、性质测试和差异测试给 agent 可核对的完成标准

Anthropic 的 Addy Osmani 于 2026-11-16 在 claude.dev 发文，介绍 Claude Code 团队如何让编码 agent 用证据验证自己的改动。文中称该团队约 90% 的代码由 Claude 编写并审查；内部在结构化文件生成任务上，用独立评分器按评分表检查，比普通提示循环最多提高 10 个成功点数，难题上收益最大。作者建议优先三类测试：端到端测试（覆盖真实用户路径，较难被“单测通过但功能坏了”绕过）；性质测试（用 fast-check、Hypothesis、proptest 等生成大量输入，检查往返编码、不变量、幂等和等价性）；差异测试（在迁移场景用旧系统当 oracle，对随机输入或生产流量抽样对比，并归一化空白等无关差异）。团队实践包括：把启动模拟器或本地服务的步骤写成仓库里的 `verify` skill，在提交前让 Claude 像人一样跑一遍应用；检查失败时 Claude 最多自行修复三轮，仍失败就交给人；由代码所有者编写检查项，并从 diff 触发可靠性清单（文中称有 39 项）；审查规则从默认/基线分支读取 REVIEW.md，不允许本次改动修改评判自己的规则；提交闸门有关闭、观察和强制三档，观察档只记录本会拦截的提交以便先排除误报。约 90% 占比、评分提升和内部闸门效果均为团队自述或内部测试，本机未核实，也未在自己的仓库里套用这些流程。
