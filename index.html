论坛：UE 5.7.4 / 5.8.4 里 AlphaHoldout 会留下黑色剪影，分离半透明并给接收材质加微弱 IOR 后可挖洞

作者 @caste117 想在编辑器视口里用 AlphaHoldout 给半透明平面挖洞，直接看到后面的不透明墙和地面。他先在 UE 5.7.4 遇到问题，随后在 5.8.4、Deferred、DX12、SM6 上复现。测试场景是一块橙色半透明平面前放一个 AlphaHoldout 立方体，平面后再放不透明墙；两种材质都是 Unlit、Before DOF、Opacity = 1，平面的 Translucency Sort Priority 为 0、立方体为 1，并且已打开 Alpha Output 与 Support Primitive Alpha Holdout (Deferred)。当平面的 Refraction Method 为 None 时，立方体只会留下黑色剪影。他在 5.8.4 上把平面的 Refraction Method 改成 Index Of Refraction、IOR 设为 1.01，并在 Output Log 执行 r.SeparateTranslucency 1 与 r.Translucency.StandardSeparated 1 后，可以看到墙和地面从挖洞处透出；若把 r.Translucency.StandardSeparated 改回 0，或把折射方法改回 None，黑色剪影会回来。文档里的 AlphaHoldout 小节只写了背景应从洞中透出，没有提到这两条控制台变量或 distortion pass。作者还指向更早的帖子：该效果在 5.4 可用，5.5 / 5.6 已出现同样的黑色剪影。他询问版本之间行为是否改过，以及在接收材质保持 Refraction Method = None 时有没有官方支持的做法，因为并不需要折射，也不想只为挖洞多开一个渲染通道。发帖时还没有回复。

    论坛：开启 Nanite Tessellation 后，硬件光追阴影对不齐置换后的表面（社区解释原因）

    作者 @HN1214 报告：在 UE 5.6 / 5.8 上使用 Lumen 与硬件光线追踪时，打开 Nanite Tessellation 后能看到网格上的置换，但光线追踪阴影对不齐置换后的表面。这个问题在侧光特写镜头里尤其明显，对影视镜头很关键。他询问更新的引擎版本是否已修复，若仍在开发则目标版本是什么。次日 @glitchered 给出社区技术解释（并非 Epic 官方答复）：Nanite 置换是实时变换的可视几何，而光线追踪依赖放进加速结构（BVH）里、预先变换好的静态或“动态”几何；Nanite 细节太多，难以即时重建 BVH，因此会使用更低分辨率的代理 BVH，这份代理不会为虚拟置换后的几何计算正确阴影，所以对不齐。答复认为这需要较长时间才能解决，帖中没有给出已验证的变通，也没有官方修复或目标版本。

VideoRNG：用生成式视频模型做出可重打光的神经高斯资产（论文）

Bowen Xue、Saeed Hadadan、Fabrice Rousselle、Ravi Ramamoorthi、Zahra Montazeri、Miloš Hašan 的论文于 2026-11-19 提交 arXiv（编号 2611.25338，学科 cs.CV、cs.GR；作者单位包括 NVIDIA、University of Manchester、UC San Diego）。作者认为网格加紧凑 PBR 材质难以表达细几何或复杂光传输带来的外观，而现有高斯溅射生成方法通常把固定光照烘焙进外观。VideoRNG 是一个两阶段方法：先把预训练视频扩散骨干微调成视频生成器，在已知位姿、相机和光照下生成结构化 RGBA 转台序列；再用从预训练视频扩散骨干初始化的前馈重建模型，把选定转台帧的 video-VAE 潜变量直接映射到带学习神经外观特征的数百万各向异性高斯。共享方向解码器和随机高斯光线追踪器把该表示（文中称为 rtRNG）变成新视角和新光照下的辐射。为在学习几何时保留高频外观，作者引入 depth-anchored appearance training，并用前景 token 选择和代价感知的分布式采样来降低百万级高斯重建的开销。论文摘要称该方法可由文本提示或单张图像生成完整、可重打光的 3D 资产，并展示毛皮、羽毛、蛛网等可交互渲染、重打光并放入场景的例子。图 1 说明中，作者报告在 NVIDIA RTX A6000 上、每资产解码器隐层宽度 64、1280×720、1 spp 时每帧约 50 ms；该耗时为作者实验数据，本机未复现。arXiv 摘要页没有 Comments 字段，也未见官方代码仓库或项目主页。

论坛：UE 5.8/5.9 摄像机切镜帧上，TSR 未写入的 mip 1 会让 Tonemap 采到过期画面（含修复建议）

作者 @Michael.Edwards 报告：在开启 TSR、运动模糊且 r.MotionBlur.HalfResInput=1（默认）时，摄像机切镜的那一帧画面边缘会出现一帧旧画面残影；把抗锯齿改成非 TSR，或设 r.MotionBlurQuality=0，残影会消失。根因是 5.8 起 TSR 会为运动模糊预过滤分配半分辨率 mip 1，但写入与分配是分开的：PassInputs.bGenerateOutputMip1 决定分配，还要加上 PassConfig.MotionBlurValidInCurrentFrame 才写入。切镜帧上 View.bCameraCut 或 View.bPrevTransformsReset 会使 MotionBlurValidInCurrentFrame 为假，于是 mip 1 仍占用池化纹理里的旧内容（常常是另一台摄像机的画面），输出 SRV 却覆盖两个 mip。切镜帧会跳过运动模糊，Tonemap 直接采样 TSR 输出；色差等会放大 UV 的导数 LOD，在屏幕边缘把过期的 mip 1 混进来。作者用 RenderDoc 确认切镜帧上 TSR.History.Color 的 mip 1 是旧帧，下一帧 mip 1 被重新写入后画面恢复。建议在未写入 mip 1 时把输出 SRV 限制为 mip 0，或在已分配时始终写入 mip 1，或让 Tonemap 用 SampleLevel(..., 0)。原文询问是否已在后续改动中修复、能否进 5.8.x 热修或 5.9；发帖时没有 Epic 回复。平台为 Windows。

Unity 6000.6.10f1：Forward+ / Deferred+ 不再处理远平面外的光与探针，并修复多处灯光裁剪

Unity 官方发布说明写明 6000.6.10f1 于 2026-11-19 发布，changeset 为 40e81493c67d。改进方面：URP 的 Forward+ 与 Deferred+ 渲染路径不再处理只在远平面之外、或位于正交相机近平面之前的那部分灯光与反射探针。变更方面：FreeType 更新到 2.15.0，为 macOS 上镜像的 Apple Color Emoji 字形提供支持，并略微改变 Hinted Smooth 与 OS Default 字体渲染模式的文本外观；Clamped 模式下的 Content Size Fitter 在 Horizontal / Vertical Layout Group 关闭 Control Child Size 时，会保持大于内容的尺寸，而不再把组收缩到子物体大小（UUM-159240）。修复中与渲染和安全相关的包括：Graphics.RenderSpriteInstanced 在 MaterialPropertyBlock 里设置 _MainTex 时不再画 Sprite 自身纹理（UUM-158701）；Android 将 Bouncy Castle 从 1.70 升到 1.86，Keystore Manager 新建密钥改为 4096-bit RSA 与 SHA256withRSA（已有密钥不变），OpenJDK 从 17.0.18+8 升到 17.0.21+9 以应对被泄露的 eMudhra 中间证书，并把 NDK API level 提高到 26；DirectX 12 为大纹理在单帧多次更新导致的崩溃提供修复，并在为 Android 目标烘焙 Entities Graphics 光照贴图时增加 CopyTexture 校验；修复 macOS 上 Unity Compute light baker 可能错误烘焙探针遮挡，以及遮挡剔除在极多 occludee 场景中的崩溃；修复 Forward+ / Deferred+ 下聚光灯边缘块状缺口、靠近近平面或屏幕边缘时点光/聚光灯缺失、以及相机后方聚光灯顶部被裁掉等问题；还修复 Unity Transport WebSocket 的栈损坏与无效握手后的越界访问（UUM-160664），以及 FreeType 畸形可变字体越界读取漏洞 CVE-2026-23865（UUM-140975）。发布说明同时列出已知问题，例如在 Baking Sets 之间切换活动场景时的 IndexOutOfRangeException 与编辑器崩溃（UUM-161251），以及若干 Mecanim / Prefab / Search 崩溃。本机未安装或回归测试该版本。

论坛：UE 5.8 部分 Masked 材质会忽略 Opacity Mask（bCanMaskedBeAssumedOpaque 被置真）

作者 @lyaflora 在空白项目中复现：复制引擎自带的 Niagara 默认精灵材质 DefaultSpriteMaterial（Engine/Niagara/DefaultAssets），把 Blend Mode 改为 Masked，并把 Opacity Mask 设为 0 后，预览网格仍完全可见，像是 Opacity Mask 为 1。作者发现出问题的材质里 bCanMaskedBeAssumedOpaque 为真，生成的 HLSL 里 PixelMaterialInputs.OpacityMask 在多处被写成 1.0f。按另一帖提供的 C++ 修复函数跑完后，该标志会变为假、HLSL 也暂时正确，但预览外观仍不变；一旦再改材质并 Apply，标志又会被重置为真，HLSL 再次写错。给该故障材质做实例、并在实例上把 Blend Mode 设为 Masked，实例侧可以正常工作，父材质仍然是坏的。作者试过关闭 Substrate、改 GBuffer Format 等项目设置，都没有解决问题。原文指向一篇关于 5.8.1 旧材质忽略 Opacity Mask 与 AO 的相关帖，发帖时没有 Epic 回复。平台为 Windows。

  • 若启动就在 splash 阶段报 ShaderCompilerEditor 的全局着色器错误，先查看 Saved/ShaderDebugInfo 里 FLumenPTVisualizeHardwareRayTracingRGS / FLumenPTInitialSamplingRGS 的日志，对照是否出现 UnpackSubstrateHeaderIn、SubstrateDeferredLighting 或 FMegaLightsMaterial.GBuffer 报错
  • 在问题修复前，不要把“LumenPT + MegaLights + World Cache”当作可在主工程默认开启的组合
