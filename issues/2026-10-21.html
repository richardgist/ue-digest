图形渲染渲染移动端

Nanite / Lumen / VSM / MegaLights / TSR：UE5.8 原理、预算与行星场景踩坑

COLONIZED / colonized.work发布:2026-10-13适用版本:UE 5.8
图形渲染渲染

用 Epic 文档数据梳理五套系统：Nanite 实例/材质/光追限制；Lumen 约 4ms@1080p/60 的主机预算与 Lumen Lite；VSM 缓存失效点；MegaLights 近似恒定成本与质量回落；TSR 收敛延迟。作者在行星场景中指出：GPU 动态生成、无 SDF 的地形对软件 Lumen「不可见」；过密小网格会生成海量 Surface Cache cards 导致起飞时 GPU timeout，提高生成 card 的最小网格尺寸后超时消失且关键反弹光仍在。

值得试的点

  • 软件 Lumen 场景若有程序化/动态地形黑斑：检查是否缺少 Mesh Distance Field，或改测 HWRT 路径
  • 荒漠类碎石场景若 Lumen 导致 GPU timeout：提高进入 Surface Cache 的最小网格尺寸，再对比远景反弹光是否可接受
  • 对照文中预算表设定 GI/Reflection Scalability，不要把「Nanite=无限面数」当出货假设

UE 5.8 渲染性能笔记：用 Medium GI 选 Lumen Lite，并独立压测 GI/反射

Game Development Constitution发布:原文未标注（面向 UE 5.8）适用版本:UE 5.8（文中标注 Lumen Lite 为 Beta）
图形渲染渲染

实操向 Lumen 选型：高画质 Lumen 给有余量的目标；UE 5.8 的 Lumen Lite 为 Beta，Medium GI（sg.GlobalIlluminationQuality 1）会走 Irradiance Field Final Gather（r.Lumen.FinalGatherMethod 0）换更快、更低质量的 GI。Medium 反射质量会关 Lumen Reflections、光滑面改 SSR，粗糙高光仍可来自 Lumen GI。强调从 BaseScalability/设备档起步，用 profilegpu 确认 Lumen pass 后再分别 A/B GI 与反射档，并注意 async compute 重叠会让单 pass 计时失真。

值得试的点

  • 要试 Lumen Lite：先把 sg.GlobalIlluminationQuality 设为 1，确认 r.Lumen.FinalGatherMethod 为 0，再量 GPU 帧时
  • 反射与 GI 分档 A/B（sg.ReflectionQuality 与 sg.GlobalIlluminationQuality 分开扫），不要一次改完所有 Scalability
  • 压测时临时关 Lumen async compute 只为隔离；结论要以恢复重叠后的整帧时间为准

官方文档：Android Device Profile 匹配规则与 Scalability 覆盖

Epic Games 官方文档发布:原文未标注（UE 5.8 文档）适用版本:UE 5.8
图形渲染移动端

说明 Android 上 Device Profile 与 Scalability 如何按硬件定制渲染：配置读取优先级（Engine/Project × Base/Android）；标准 Android_Low/Mid/High 与按 GPU 族细分的 profile；启动时按 MatchProfile 规则（机型/厂商/GPU/Android/Vulkan 等比较）选档。VulkanAvailable 同时看打包是否启用与设备是否满足工程要求的 Vulkan；文档建议 Android 9+ 再开 Vulkan。可用项目内 AndroidScalability.ini / AndroidDeviceProfiles.ini 覆盖，设备档用 sg.* 引用 Scalability 组。

值得试的点

  • 在 Project/Config/Android/ 覆盖 AndroidDeviceProfiles.ini 与 AndroidScalability.ini，避免直接改 Engine 安装目录
  • 新增 MatchProfile 时按同 GPU 族从低到高插入，防止被更宽泛规则抢先命中
  • 预览移动画质时优先改 Scalability 组，再在 profile 里用 sg.ShadowQuality 等引用，以便编辑器 Preview Rendering Level 一致
